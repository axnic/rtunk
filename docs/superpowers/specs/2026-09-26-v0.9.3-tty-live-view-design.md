# v0.9.3 TTY live view: Design

**Status:** design agreed with the user in conversation (2026-09-26) before this spec was written.
This is sub-project 3 of 4 of ROADMAP `v0.9`; see Scope.

## Scope

ROADMAP `v0.9` ("Output and UX", [ROADMAP.md](../../../ROADMAP.md), [docs/ux.md](../../ux.md)) is
decomposed into four sub-projects, each with its own spec and plan:

1. Event stream + plain renderer
   ([v0.9.1 spec](./2026-09-26-v0.9.1-event-stream-plain-renderer-design.md), implemented).
2. `--format human|sarif|json` on `check` and `fmt`
   ([v0.9.2 spec](./2026-09-26-v0.9.2-format-flag-design.md), implemented).
3. **TTY live view** (this spec).
4. Filtered `linters list` / `actions list` (implemented).

This spec covers only #3. It is split in two parts that land in this order: **3a**, additive engine
events (`pkg/trunk/engine`), and **3b**, the live renderer, its terminal handling and the CLI wiring
(`internal/cli/render`, `internal/cli`). The live view is a `Renderer` decorator over the existing
renderers; it adds no fourth format.

## Goal

On an interactive terminal, `check` and `fmt` draw the docs/ux.md live area on stderr while the run
progresses: a header with a percentage bar and elapsed time, a per-linter tree of in-flight files,
and install rows with byte progress. When the run ends the area is erased and the stdout report
(`human`, `json` or `sarif`) is written exactly as today. Outside that case (non-terminal stderr,
`TERM=dumb`, `--no-progress`) the v0.9.1 stderr progress lines are emitted byte for byte as before.
Exit codes, stdout content and run logs are unchanged.

## Current state

- `pkg/trunk/engine/engine.go`: `Phase` is `Running | Done | Skipped | Failed`. `Event` carries
  `Linter, Phase, Findings, ChangedFiles, Note, Err, File, Files`. `Run` builds jobs per linter
  sequentially in one producer goroutine (`buildJobs`), which sends `Skipped`/`Failed` events
  directly and, on the first command that needs tools, calls `resolveShimDirs` (linter tools) and
  `resolveRuntimeShimDir` (parser runtime). Both call `download.Download`, range over its channel and
  keep only the first `download.Failed` error: every `Started`/`Progress`/`Done` event is discarded.
  Workers then run `runJob`, which sends one `Running` event (`File` is the batch joined with `", "`)
  and, once `remaining` reaches zero, the linter's single terminal event. When `Env.Log` is set,
  every event passes `logLinterEnd`, which already ignores everything but `Done|Skipped|Failed`
  (`default: return`).
- `pkg/trunk/download/download.go`: `Event{Ref{Category, ID, Version}, Phase, Bytes, Total int64,
Err}`, `Phase` is `Started | Progress | Cached | Done | Failed`; `Total` is `-1` when the server
  sent no Content-Length. One `Download` call for a runtime+package tool emits events for the
  runtime ref first (`fetchToolRef` fetches the runtime, then sends `Started` for the tool itself,
  which has no `Progress`), so the tool's row can only appear after its runtime's row is done.
  `Cached` refs emit no `Started`.
- `internal/cli/render/base.go`: `base.Event` returns early only for `Running`; any other phase is
  recorded in `linters`/`files` and writes a progress line. Adding phases without touching it would
  count them as linters that emitted a terminal event and print an empty progress line.
  `drainRunEvents` (`check.go`) and `collectChangedByLinter` (`fmt_stability.go`) already `switch` on
  the phase and ignore unknown ones.
- `internal/cli/format.go`: `newRenderer(format, stdout, stderr, kind, noProgress)` builds a
  `render.Options` and calls `render.New`; `isTerminal(w)` is `ModeCharDevice` on an `*os.File`.
  `check.go` builds up to two renderers (`check --fix` formatter pass, then the check pass);
  `fmt.go` builds one, and `--verify-stable` feeds several engine runs to it.
- `--no-progress` exists on `check` and `fmt`. `--ascii` and `--live-height` do not exist.
  docs/ux.md ("Live view", "Spinners", "Implementation") is the authoritative UX target; "Non-TTY
  fallback" is implemented.
- go.mod dependencies are kong, yaml.v3 and testify; the build sandbox has no network.

## Design

### Decisions

- **A. Engine events are additive (3a).** Nothing new is derivable from the current stream (no total
  before completion, no per-job end, no install visibility); additive phases keep every existing
  consumer working once it ignores them.
- **B. A decorator, not a fourth format (3b).** `render.NewLive(inner, opts)` wraps any renderer, so
  the stdout report of `human|json|sarif` is untouched and the live code holds presentation state
  only (v0.9.1 rule).
- **C. Pure frame, thin screen.** The frame is a pure function of state, size, clock and glyph set,
  so it is golden-testable; the ANSI cursor handling is a tiny separate type.
- **D. Layout follows docs/ux.md**, with the deviations recorded in "Deviations from docs/ux.md".
- **E. The live area is on stderr.** stdout stays the report channel for every format, and
  `--no-progress` disables the live view entirely.
- **F. No new dependency.** `golang.org/x/term` is not added: the build sandbox has no network and
  the terminal size is one `ioctl`.

### 1. Engine events (3a)

New phases, appended after `Failed` so existing values do not change; all are non-terminal:

```go
const (
    Running Phase = iota
    Done
    Skipped
    Failed
    Planned         // once per linter, after buildJobs, when it queued at least one job
    JobDone         // one job finished (any outcome), after runBatch
    InstallStart    // a download began for Item
    InstallProgress // Bytes/BytesTotal update for Item
    InstallDone     // the download for Item ended (success or failure)
)
```

New `Event` fields (no clash with existing ones; `Total` is a job count, the byte counters are
named separately):

| Field        | Type   | Phases                   | Meaning                                                                |
| ------------ | ------ | ------------------------ | ---------------------------------------------------------------------- |
| `Total`      | int    | `Planned`                | number of jobs queued for the linter                                   |
| `Batch`      | bool   | `Planned`                | true when any of the linter's jobs has more than one file in its batch |
| `Item`       | string | `Install*`               | `category/id`, e.g. `tools/shfmt`, `runtimes/node`                     |
| `Bytes`      | int64  | `InstallProgress`        | bytes received so far                                                  |
| `BytesTotal` | int64  | `InstallStart\|Progress` | Content-Length, `-1` when unknown (`InstallStart` always `-1`)         |

Emission points:

- **`Planned`**: in `Run`'s producer goroutine, right after each `buildJobs` call that returned at
  least one job: `Event{Linter, Phase: Planned, Total: len(linterJobs), Batch: <any len(j.batch) > 1>,
Files: <linter's matched files>}`. `buildJobs` does not return its `relFiles` (its `j.files` is the
  per-directory subset, shadowed in the group loop), so `Files` is the union of the jobs' `j.files`,
  sorted; this avoids changing `buildJobs`' return type. A linter that got only `Skipped`/`Failed` events emits no
  `Planned`.
- **`JobDone`**: in `runJob`, immediately after `runBatch` returns and before `state.mu` is taken:
  `Event{Linter, Phase: JobDone, File: strings.Join(j.batch, ", ")}` (same string as `Running`, so a
  consumer pairs them). Sent for success and failure alike. Because it precedes the `remaining--`
  that can fire the terminal event, a linter's last `JobDone` always precedes its `Done`/`Failed`.
  Jobs skipped after a sibling failed (`state.failed`) and jobs abandoned on `ctx` cancellation
  send neither `Running` nor `JobDone`.
- **`Install*`**: `resolveShimDirs` and `resolveRuntimeShimDir` gain an `emit func(Event)` parameter
  (`buildJobs` passes `func(ev Event) { events <- ev }`; both run in the producer goroutine, which
  is what may block on the channel today, so no new goroutine or ordering hazard). Inside the
  `range evs` loop they translate `download.Event` to engine events with
  `Item = ref.Category + "/" + ref.ID` taken from `ev.Ref` (a runtime+package tool therefore yields
  rows for both `runtimes/node` and `tools/<id>`):

  | `download.Phase` | Engine event                                                  |
  | ---------------- | ------------------------------------------------------------- |
  | `Started`        | `InstallStart` (`BytesTotal: -1`)                             |
  | `Progress`       | `InstallProgress` (`Bytes`, `BytesTotal` from `Total`)        |
  | `Done`           | `InstallDone`                                                 |
  | `Failed`         | `InstallDone`, only if that item's `InstallStart` was emitted |
  | `Cached`         | nothing (no row, no count)                                    |

  A `Failed` download still returns its error exactly as today (`return nil, ev.Err`), and the
  linter still gets its `Failed{Note: "resolving tools"}` or `Skipped` event from `buildJobs`; the
  extra `InstallDone` only closes the row so it does not stay on screen, and the "only if started"
  guard keeps starts and dones balanced (a failed runtime makes `fetchToolRef` send `Failed` for a
  tool ref that never started). The set of started items is local to the range loop.

- Engine-side `Env.Log` is unaffected: `logLinterEnd` keeps its `default: return`, which already
  ignores the new phases; an engine test pins it so a future edit cannot log them.

**Existing consumers ignore the new phases** (must change in this sub-project):

- `base.Event` (`internal/cli/render/base.go`) currently drops only `Running`. It returns early for
  every phase except `Done`, `Skipped` and `Failed`, so a `Planned`/`JobDone`/`Install*` event never
  counts as a linter with a terminal event and never writes a progress line.
- `drainRunEvents` and `collectChangedByLinter` already switch on `Done|Skipped|Failed` and need no
  change; a test pins it.
- `logLinterEnd` (`engine.go`): see above, unchanged behavior.

### 2. Live state (`internal/cli/render/live.go`)

`liveState` is a plain struct, mutated by `Event`, read by `frame`; the live decorator guards it with
one mutex because the redraw goroutine reads it while the CLI goroutine writes it.

```go
type liveState struct {
    kind       Kind                // Check -> "Checking", Fmt|FmtCheck -> "Formatting"
    start      time.Time           // NewLive time; elapsed = now - start
    total      int                 // sum of Planned.Total + installs started
    done       int                 // JobDone + InstallDone (+ reconciliation, below)
    linters    map[string]*lintRow // present from the first Running until the terminal event
    installs   []*installRow       // start order; removed on InstallDone
}
```

- `Planned`: `total += Total`; the linter's row data (`Total`, `Batch`, `jobDone = 0`) is stored,
  replacing a previous entry for the same linter. Replacing, not accumulating, is what makes
  `--verify-stable` and `check --fix` rounds behave: each round re-plans the linter, the header
  total keeps growing across rounds (each round is more work), and the per-linter mini-bar restarts.
- `Running`: the linter row is created (if absent) and the file (`ev.File`) is added to its in-flight
  list. A linter is therefore shown only while a worker is on it; queued linters with no worker do
  not occupy lines. In-flight entries are kept in arrival order.
- `JobDone`: `done++`, the linter's `jobDone++`, the file is removed from the in-flight list.
- `InstallStart`: `total++`, a row is appended (`Item`, `Bytes=0`, `BytesTotal=-1`).
  `InstallProgress` updates it. `InstallDone`: if the row exists, `done++` and it is removed; a
  `InstallDone` for an unknown item is ignored (never counts).
- `Done|Skipped|Failed`: the linter row is removed. On `Done` and `Failed` the linter's unfinished
  jobs are credited to the header (`done += Total - jobDone`): after a failure the engine never runs
  the linter's remaining jobs and never sends their `JobDone`, and without this credit the bar would
  never reach 100%. Nothing is credited for a linter with no `Planned` entry.
- Every other event and phase is ignored by the state.
- Header total is `Planned` totals plus installs started so far (it grows when an install starts:
  the engine resolves tools linter by linter, so later installs are unknown until reached);
  percentage is `round(100*done/total)`, `0` when `total == 0`.

### 3. Frame (pure)

```go
func (s *liveState) frame(width, height int, now time.Time, ascii bool) []string
```

Returns at most `height` lines, each at most `width-1` runes (the last column stays free so a full
line cannot trigger a terminal auto-wrap; width is counted in runes, wide CJK paths are a known
ceiling). `height` is already resolved by the caller (section 5); the function clamps it to a
minimum of 3. No ANSI in this version: the live area uses no color, at most bold on the header verb
if it is one `paint` call, otherwise nothing (`NO_COLOR` therefore needs no handling here).

**Header**, one line: `<verb> <pct>% <bar> <done>/<total> · <elapsed>`

```text
Checking   39% ⣿⣿⣿⣿⣿⣿⣿⣿⣿⣿⣿⣷⣀⣀⣀⣀⣀⣀⣀⣀⣀⣀⣀⣀⣀⣀ 12/31 · 3.2s
```

- `verb` is `Checking` for `Check`, `Formatting` for `Fmt` and `FmtCheck`, padded to 10 so the bar
  does not move; `pct` is right-aligned on 3 columns.
- Elapsed is `%.1fs` under one minute, `NmSSs` from one minute (`1m04s`).
- The bar takes every column not used by the fixed text (prefix, ` done/total · elapsed`, spaces).
  When `width < 40` the bar and its spaces are dropped and the counter stays:
  `Checking   39% 12/31 · 3.2s`. If even that does not fit, the line is truncated to the width.
- **Braille resolution: 7 glyph states per cell, 6 sub-steps per cell.** Cell states, empty to full:
  `⣀ (0xC0)`, `⣄ (0xC4)`, `⣤ (0xE4)`, `⣦ (0xE6)`, `⣶ (0xF6)`, `⣷ (0xF7)`, `⣿ (0xFF)`, i.e. the
  glyphs that fill the eight dots bottom-up two dots at a time, keeping the empty cell visible as
  `⣀`. With `cells` cells: `steps = done*cells*6/total` (integer, clamped to `cells*6`); the first
  `steps/6` cells are `⣿`, the next cell is state `steps%6`, the rest are `⣀`. `total == 0` renders
  all `⣀`. This deviates from docs/ux.md's "8 steps per character" (see Deviations).
- **ASCII bar**: `[` + `=` per filled cell + spaces + `]`, one step per cell (no partial cell); the
  brackets are inside the bar's column budget.

**Per-linter tree.** Linters sorted by name, each a block, then install rows in start order. The
name column is as wide as the longest linter or install name currently shown, capped at 20 (longer
names are cut with the ellipsis). Indentation is two spaces.

```text
  markdownlint   ⣿⣿⣷⣀⣀ 7/47
    ⠋ docs/superpowers/plans/2026-09-26-run-logs.md
    ⠙ pkg/trunk/config/ARCHITECTURE.md
  golangci-lint  ⠹
    pkg/trunk/actions/run.go, pkg/trunk/actions/run_log.go (+151)
↓ shfmt          ⠛ 4.1/12 MB
```

- Linter whose `Planned.Batch` is false: `  <name>  <5-cell mini-bar> <jobDone>/<Total>`, then one
  line per in-flight file `    <spinner> <path>` (Dots spinner). The mini-bar uses the same 6
  sub-steps per cell as the header (30 steps).
- Linter whose `Planned.Batch` is true: `  <name>  <Dots spinner>` and nothing else on the line (no
  mini-bar, no counter, no "batch" label), then one line `    <a>, <b> (+N)` listing the first two
  in-flight files and `(+N)` for the remaining count, omitted when N is 0. The in-flight strings are
  the `Running.File` batch strings split on `", "` (a file name containing `", "` is split
  wrongly: known ceiling, the engine joins that way today). Multiple in-flight batches of one
  linter (several run-from directories) are flattened into one list.
- **Install rows**: `↓ <name>  <Sand spinner> <bytes>`, where the `↓` glyph sits in the
  indentation slot (no padding before it) so linter names stay aligned. `<name>` is the id part of
  `Item`, after the `category/` prefix (`shfmt`, `node`). `<bytes>` is
  `4.1/12 MB` when `BytesTotal >= 0` and `Bytes > 0`, otherwise nothing (the spinner alone). Units
  scale by 1024 from the total's magnitude (`B`, `KB`, `MB`, `GB`); the received value has one
  decimal, the total none when 10 or more. When `InstallDone` arrives the row is removed: the "switch
  to the normal style in place" of docs/ux.md is realized as disappearance, since the linter row
  appears only with its first `Running`.
- No "waiting for runtime" text in this version. The download package orders runtime before tool
  internally and only emits the tool's `Started` after the runtime is done, so the engine has no
  waiting state to report. **Known gap**, recorded here and in docs/ux.md.
- **Path shortening**: a path longer than the space left on its line is cut in the middle with `…`
  (`...` in ASCII), keeping the base name whole when possible:
  `docs/superpowers/…/2026-09-26-run-logs.md`. Lines are truncated to the width as the last step.
- **Overflow**: the lines of the tree share `height - 1` lines. Blocks are shown in order while they
  fit; the first block that does not fit is shown as far as it goes (its linter line, then as many
  file lines as fit; trimmed file lines are not counted), and every block after it is folded into
  one last line `  +N workers`, `N` being the number of hidden linter blocks and install rows. That
  line takes one of the `height - 1` lines, so a frame is never longer than `height`.
- **Quiescence**: when there are no linter blocks and no install rows and `done >= total` (nothing
  in flight, nothing planned that is not finished), `frame` returns no lines. The screen then erases
  the area and stops drawing until the next event. This is what keeps the area from sitting on a
  stale `100%` header when the CLI writes its own stderr messages after the last event
  (`warnIfRecentOverlap`, log warnings): the area is already gone by the time it does. The same
  rule can blank the area briefly between two linters whose resolution is sequential; a blank only
  shows if it coincides with a 100 ms tick and the header returns on the next event. Known
  imprecision, ceiling: a small delay hysteresis if it proves visible.

**Spinners** use the docs/ux.md frame sets verbatim (`Dots` 10 frames, `Sand` 35 frames, constants
in `live.go`). The frame index is computed from the clock, `frames[t/interval % len(frames)]` with
`t = now.UnixMilli()`, `Dots` interval 80 ms and `Sand` interval 70 ms, so all rows of a kind are in
sync and `frame` stays pure (tests pass a fixed `now`). ASCII spinner: `|/-\` for both kinds, 80 ms
interval, and `v` replaces `↓`. `DotsVariant` stays reserved.

**ASCII glyph set** (`ascii == true`): `[=== ]` bar, `|/-\` spinner, `v` install glyph, `...` for `…`,
`-` for the `·` between counter and elapsed. `+N`, `(+N)` and `+N workers` are already ASCII.

### 4. Screen (ANSI redraw)

```go
type screen struct {
    w     io.Writer
    size  func() (cols, rows int)
    lines int // lines currently drawn
}

func (s *screen) draw(frame []string)  // redraw in place
func (s *screen) clear()               // erase the area, cursor back at its top
```

- Every line of the area ends with `\n`, so after a draw the cursor sits on the line below the
  area. `draw` writes one buffer in a single `Write` (no tearing): cursor up `lines` (`\x1b[<n>A`,
  omitted when `n == 0`), `\r`, then for each new line `\x1b[2K` + line + `\n`; if the new frame is
  shorter than the previous one, the leftover `k` lines are erased with `\x1b[2K\n` each and the
  cursor goes back up `k` (`\x1b[<k>A`). `lines` becomes `len(frame)`.
- `clear` is `draw(nil)`: up `lines`, erase every line, up again, `lines = 0`; the cursor ends where
  the area started, ready for the report.
- **The cursor is never hidden** (no `\x1b[?25l`), so nothing has to be restored on exit or on a
  crash, and no state outlives the process. The visible cursor blinking on the line below the area
  is accepted.
- The size is queried on every tick (below). A shrinking terminal is handled by the frame being
  recomputed at the new width; content already wrapped by the terminal is out of scope (the last
  column stays free precisely to avoid that).

### 5. Decorator, options, detection

```go
type LiveOptions struct {
    Out     io.Writer          // stderr
    Size    func() (cols, rows int) // terminal size, queried each tick
    Height  int                // --live-height; <= 0 means half the terminal height
    ASCII   bool
    Command Kind
    Now     func() time.Time   // clock, time.Now by default
}

func NewLive(inner Renderer, opts LiveOptions) Renderer
```

- `Event(ev)`: locks, updates `liveState`, forwards `ev` to `inner`. `inner` is built by the CLI with
  `NoProgress: true`, so its progress lines do not collide with the live area; the plain lines
  exist only in the non-live path. `inner.Event` is called from the same goroutine, in order.
- `NewLive` starts one goroutine with a 100 ms ticker (about 10 Hz). Each tick: read
  `Size()`, compute `height = Height` or `rows/2`, clamp to at least 3 (bar plus 2), compute
  `frame(cols, height, Now(), ASCII)` under the lock, `screen.draw`.
- `Close(s)`: signals the goroutine to stop and waits for it (`sync.WaitGroup`), calls
  `screen.clear()`, and only then `inner.Close(s)`, so the stdout report never interleaves with the
  live area and its bytes are exactly what `inner` alone would write. No final frame is drawn (the
  area is being removed); the "once more on Close" is the erase. `Close` is idempotent for the
  goroutine and returns `inner.Close`'s error.
- **Terminal size** (`internal/cli/render/termsize_unix.go`, `//go:build unix`): `TIOCGWINSZ`
  through the stdlib `syscall` ioctl on stderr's file descriptor (`struct winsize`: rows, cols,
  two pixel fields); `termsize_other.go` (`//go:build !unix`) returns `80, 24`. The CLI passes the
  function as `LiveOptions.Size`. Because the size is read on every tick, a resize is picked up
  within 100 ms and no `SIGWINCH` handler exists. A failed ioctl yields `80, 24`.
  `golang.org/x/term` is deliberately not added: no network in the build sandbox and the ioctl is a
  few lines. `// ponytail:` ceiling noted in the code: unix only (no Windows console), upgrade to
  `x/term` if Windows or exotic platforms matter.
- **Ctrl+C**: `NewLive` calls `signal.Notify(ch, os.Interrupt)`. On the signal the redraw goroutine
  erases the area (`screen.clear()`), calls `signal.Reset(os.Interrupt)`, and re-sends `SIGINT` to
  its own process (`os.FindProcess(os.Getpid())` then `Signal(os.Interrupt)`), so Go's default
  termination proceeds and the exit status is the usual one for an interrupted process. There is no
  cursor to restore because the cursor is never hidden. `Close` calls `signal.Stop(ch)` so the
  handler does not outlive the renderer (`check --fix` builds one live renderer per pass; each
  `Close` stops its own).
- **Enable decision** (pure, in `render`):

  ```go
  // LiveEnabled reports whether the live view is drawn: stderr is a terminal, --no-progress is
  // not set and TERM is not "dumb".
  func LiveEnabled(stderrIsTTY, noProgress bool, term string) bool {
      return stderrIsTTY && !noProgress && term != "dumb"
  }
  ```

  `TERM=dumb` and a non-terminal stderr take the v0.9.1 plain-line path, byte-identical. An unset
  `TERM` (empty) is not "dumb" and does not disable the view; a terminal that then mishandles the
  escapes is a user-environment issue.

- **ASCII decision** (pure): `ASCII = --ascii || !IsUTF8Locale(LC_ALL, LC_CTYPE, LANG)`.
  `IsUTF8Locale(lcAll, lcCtype, lang string) bool` looks at the first non-empty of the three (in that
  precedence) and is true when it contains `utf-8` or `utf8`, case-insensitive; all three empty is
  false (a locale-less environment gets ASCII). A non-UTF-8 locale or `--ascii` still uses the live
  redraw, with the ASCII glyph set. Only the environment reading lives in the CLI.

### 6. CLI wiring

- `internal/cli/format.go`: `newRenderer` gains `ascii bool, liveHeight int` (or a small options
  struct if the parameter list becomes unwieldy). It builds the inner renderer as today, except
  `NoProgress` is forced to `true` when live is active, then wraps:
  `live := render.LiveEnabled(isTerminal(stderr), noProgress, os.Getenv("TERM"))`;
  if `live`, `render.NewLive(inner, LiveOptions{Out: stderr, Size: <ioctl on stderr's *os.File>,
Height: liveHeight, ASCII: ascii || !render.IsUTF8Locale(...), Command: kind})`. Otherwise it
  returns the inner renderer unchanged. `isTerminal` keeps its `ModeCharDevice` implementation
  (accepting `/dev/null` as before; escapes to `/dev/null` are harmless).
- `check` and `fmt` (`checkRunCmd`, `fmtCmd`) gain two flags:
  - `ASCII bool` (`--ascii`): "Use ASCII glyphs in the live view."
  - `LiveHeight int` (`--live-height`, `env:"RTUNK_LIVE_HEIGHT"`, Kong env tag, default `0` =
    half the terminal height): "Maximum height of the live view in lines (default: half the
    terminal, minimum 3)."
    `--no-progress` disables the live view entirely, as it disables the progress lines.
- **`check --fix`** builds one live renderer per pass (the formatter pass through
  `newRenderer("human", fixOut, ...)`, then the check pass): each pass's `Close` stops its own
  goroutine and signal handler and erases its area before the next starts. The formatter pass's
  `fixOut` (real stdout or `io.Discard`) is unchanged.
- **`fmt --verify-stable`** feeds several engine runs to one renderer: each round re-plans, so the
  header total grows per round (section 2); the area is drawn until the single `Close`.
- The drain loops (`drainRunEvents`, `collectChangedByLinter`) are unchanged and keep passing every
  event to `r.Event`.
- Stderr messages the CLI writes outside the renderer (`rtunk: no files to check|format`,
  `skipPartiallyStaged`, log warnings, `warnIfRecentOverlap`) are emitted before the renderer exists
  or after the last event, when the area is empty (quiescence, section 3). A warning written while a
  run is in flight would be overwritten by the next redraw; none is written then today.

### 7. Deviations from docs/ux.md

To be applied to docs/ux.md by the implementation plan, not by this spec:

- **Braille resolution**: docs/ux.md says 8 dots per cell, 8 steps per character (100 columns = 800
  steps, mini-bar = 40 steps). The delivered bar has 7 glyph states per cell, i.e. 6 sub-steps
  (mini-bar = 30 steps): the empty cell is the visible `⣀` rather than a blank, and the states are the
  six bottom-up fills listed above. The doc's numbers change accordingly.
- **Waiting state**: "waiting for runtime node" install rows are not produced (known gap, section 3).
- **Resize**: "recomputed on SIGWINCH" becomes "recomputed every tick"; there is no signal handler.
- **Terminal library**: docs/ux.md "Implementation" names `golang.org/x/term`; the delivered code
  uses the stdlib `syscall` ioctl (section 5).
- **Cursor**: docs/ux.md says Ctrl+C must "restore the cursor"; the cursor is never hidden, so
  Ctrl+C only erases the area and re-raises the signal.
- **Color**: the live area uses no color in this sub-project; docs/ux.md's "different color" for
  install rows is deferred.

## Non-goals

- Color themes and any color in the live area; byte-progress style variants (only `4.1/12 MB`).
- OSC 8 links.
- A "waiting for runtime" state (known gap: needs the download package to expose its ordering).
- Sort by severity or any live findings count.
- `golang.org/x/term`, Windows console support (the non-unix fallback is a fixed 80x24), a
  `SIGWINCH` handler.
- Mouse or keyboard interaction, pause, or scrolling in the live area.
- Changing the stdout report of any format, exit codes, file selection, the run-log schema or the
  v0.9.1 progress-line format.
- A live view for commands other than `check` and `fmt` (no `actions run`, `toolbox download`).

## Testing

- **Frame goldens** (`internal/cli/render`, table-driven, `liveState` built from synthetic events,
  fixed `now` so spinner frames are deterministic, expected `[]string` inline or under
  `testdata/live/`):
  - header at 0%, 39% (12/31) and 100%, for `Check` (`Checking`) and `Fmt` (`Formatting`), with the
    bar cell states checked at each of the 6 sub-steps of a cell;
  - bar disappears below 40 columns and the counter stays; lines truncated to `width-1`;
  - per-file linter tree: mini-bar and `done/total`, one spinner line per in-flight file, a file
    leaving on `JobDone`, a linter disappearing on `Done`, `Skipped` and `Failed`;
  - batch linter: spinner only on the linter line and the single `a, b (+N)` line (N omitted at 0);
  - install row with `BytesTotal >= 0` (`4.1/12 MB`) and with `-1` (spinner only); row removed on
    `InstallDone`; `InstallDone` for an unknown item ignored; `Failed` install balanced by the
    engine guard (state-level test: start and done both count once);
  - header total grows on `InstallStart`; failure credit (`Failed` with unfinished jobs reaches
    100%); re-`Planned` linter (verify-stable round) resets its row and adds to the total;
  - overflow: `+N workers` with the right N, frame never longer than `height`, first oversized block
    trimmed;
  - path shortening in the middle with `…`, base name kept, ASCII `...`;
  - ASCII variant of the whole frame (`[=== ]`, `|/-\`, `v`, `-`);
  - `height` below 3 clamped to 3; quiescent state returns no lines;
  - spinner frame selection: same `now` gives the same frame for all rows of a kind, `now + interval`
    advances by one, `Dots` 80 ms and `Sand` 70 ms.
- **Screen redraw** (byte-level, `bytes.Buffer` writer): first draw has no cursor-up; second draw
  emits `\x1b[<n>A`, `\r` and one `\x1b[2K` per line; a shorter frame erases the leftover lines and
  moves back up by exactly that many; `clear` erases everything and leaves `lines == 0`; no
  `\x1b[?25l`/`\x1b[?25h` is ever written.
- **Detection tables** (pure functions): `IsUTF8Locale` over (`LC_ALL`, `LC_CTYPE`, `LANG`)
  including precedence (`LC_ALL=C` beats `LANG=en_US.UTF-8`), `UTF-8`, `utf8`, `UTF8` case
  variants, first-non-empty semantics, all empty; `LiveEnabled` over (tty, noProgress, term)
  including `TERM=dumb`, `TERM=""` and `TERM=xterm-256color`.
- **Engine** (`pkg/trunk/engine`): with a fake catalog, `Planned` is sent once per linter with the
  right `Total`, `Batch` (true only with a multi-file batch) and `Files`, and not for a linter that
  only got `Skipped`; every `Running` is followed by a `JobDone` with the same `File`, and a
  linter's last `JobDone` precedes its terminal event; `Install*` events for a missing tool
  (`InstallStart`, at least one `InstallProgress` with `BytesTotal`, `InstallDone`) using the
  existing local download test fixtures; `Cached` emits nothing; a failing download still returns
  its error and emits `InstallDone` only for started items; `logLinterEnd` writes nothing for the
  five new phases.
- **Consumers ignore new phases**: `base.Event` fed `Planned`/`JobDone`/`Install*` leaves `linters`,
  `files` and `failures` empty and writes nothing to stderr; `drainRunEvents` and
  `collectChangedByLinter` results are unchanged with the new events interleaved.
- **Non-TTY byte identity** (`internal/cli`): with a non-terminal stderr (buffer), `check` and `fmt`
  stdout and stderr are byte-identical to the v0.9.2 output for the same run, including under
  `--format json|sarif` and `check --fix`; `TERM=dumb` behaves the same; no `\x1b` byte on stderr.
- **Ordering**: with one shared buffer as both `Out` and the inner renderer's stdout, `Close` writes
  the erase sequence before the first byte of the report, and the report bytes equal the inner
  renderer alone; `Close` leaves no goroutine running (no writes after it returns).
- **CLI**: `--ascii` and `--live-height` parse on `check` and `fmt`, `RTUNK_LIVE_HEIGHT` is read,
  a non-numeric value is a Kong usage error; `--no-progress` produces no live output and no
  progress lines.
