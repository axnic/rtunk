# `rtunk check` v0.3.1 — Additional Output Formats — Design Spec

## Goal

v0.3 (`docs/superpowers/specs/2026-09-12-check-v0.3-design.md`) implemented only `sarif` and
`pass_fail` output parsing — 79/124 real trunk-io linters. This plan adds every remaining
Output-value parser where doing so, on its own, actually unlocks the linter (i.e. the linter isn't
_also_ blocked by v0.3's other documented non-goals: `RunFrom`, `SandboxType`, or an unsupported
`${...}` template var). Linters blocked by those non-goals stay `Skipped` regardless of this plan —
they need a `RunFrom`/`SandboxType` support plan (v0.3.2, not this one).

## Scoping method

Surveyed every non-generic `Output` value across the real trunk-io plugin catalog
(`~/Library/Caches/rtunk/plugins/*.json`, 129 linters), cross-referencing each command's `Output`,
`RunFrom`, `SandboxType`, and `Run` string (for unsupported `${...}` vars) against v0.3's already-
shipped skip conditions. Every schema below is grounded in a real source: either the tool's own
documented/source-verified schema, or (for `taplo` and `markdownlint-cli2`) a real sample captured
directly by running the actual tool locally (`npx @taplo/cli`, `npx markdownlint-cli2`) against a
broken fixture — never a fabricated sample, per this project's standing testing rule.

## Scope: in this plan

### Bespoke JSON parsers (11 formats, no other blocker)

| Output value   | Linter       | Real command                                                | Schema source                                                                                                                  |
| -------------- | ------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `actionlint`   | actionlint   | `actionlint -format "{{json .}}" ${target}`                 | `rhysd/actionlint`'s `error.go` (source-verified)                                                                              |
| `bandit`       | bandit       | `bandit --format json --output ${tmpfile} ${target}`        | bandit's documented JSON formatter                                                                                             |
| `buildifier`   | buildifier   | `buildifier --format=json --mode=check ${target}`           | `bazelbuild/buildtools`'s `diagnostics.go` (source-verified)                                                                   |
| `cfnlint`      | cfn-lint     | `cfn-lint -t ${target} -f=json`                             | AWS cfn-lint's documented JSON schema                                                                                          |
| `eslint`       | eslint       | `eslint --output-file ${tmpfile} --format json ${target}`   | ESLint's documented JSON formatter (eslint.org)                                                                                |
| `hadolint`     | hadolint     | `hadolint ${target} -f json --no-fail`                      | hadolint's documented JSON array schema                                                                                        |
| `haml_lint`    | haml-lint    | `haml-lint ${target} --reporter=json`                       | `sds/haml-lint`'s `json_reporter.rb`/`hash_reporter.rb` (source-verified — `JsonReporter` is literally `HashReporter.to_json`) |
| `markdownlint` | markdownlint | `markdownlint ${target} --json`                             | DavidAnson/markdownlint's documented object-keyed-by-filename schema                                                           |
| `pylint`       | pylint       | `pylint --output ${tmpfile} --output-format json ${target}` | pylint's legacy `JSONReporter` (source-verified field names)                                                                   |
| `rubocop`      | standardrb   | `standardrb ${target} --format json`                        | RuboCop's `json_formatter.rb` (source-verified — standardrb wraps rubocop, same formatter)                                     |
| `stylelint`    | stylelint    | `stylelint -f json ${target}`                               | stylelint's documented JSON formatter                                                                                          |

### `sarif_uri` — alias, not a new parser

| Output value | Linter  | Real command                                                               |
| ------------ | ------- | -------------------------------------------------------------------------- |
| `sarif_uri`  | checkov | `checkov -f ${target} -o sarif --output-file-path ${tmpfile}, --soft-fail` |

`ReadOutputFrom: tmp_file` already reads the file `${tmpfile}` names into `out` before any
Output-specific parsing runs (`run.go`'s existing `runOneInvocation` behavior, unchanged since
Task 3). checkov's `-o sarif --output-file-path <path>` writes genuine SARIF to that path — so
`sarif_uri` needs zero new parsing code, just one more `case "sarif_uri":` in `run.go`'s dispatch
that calls the existing `ParseSARIF`, exactly like `case "sarif":` does.

### Two formats needing their own bespoke (non-JSON) parser

| Output value     | Linter     | Real command                                                                   | Real captured/verified shape                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------- | ---------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `regex` (custom) | perlcritic | `perlcritic --verbose 'path=%f,line=%l,col=%c,code=%p,message=%m\n' ${target}` | Comma-separated `key=value` pairs, one line per finding — **not** the shared colon-format below. Confirmed directly from the real `Run:` string in the plugin catalog (perlcritic's own `--verbose` format-string flag), not secondhand research.                                                                                                                                                                        |
| `regex` (custom) | taplo      | `taplo lint ${target}`                                                         | Multi-line `codespan_reporting`-style block. **Real sample captured locally** (ran `npx @taplo/cli lint` against a broken TOML file): `"error: invalid TOML\n  ┌─ <path>:<line>:<col>\n  │\n<n> │ <source line>\n  │ <caret-underline> <label>\n"`, one or more blocks per invocation, plus unrelated `INFO`/`ERROR` tracing-crate log lines mixed into the same stream that must be ignored, not mistaken for findings. |

Both are still `Output: "regex"` in trunk's own data model (there is no separate Output value for
them — trunk's closed-source binary evidently special-cases every "regex" linter internally by its
own name, which this project's data has no visibility into). Since `run.go`'s dispatch has always
been by `(Output, linter)` pair already — see below — giving these two their own dedicated parser
functions, selected by linter name, is a refinement of "one generic regex parser" (the framing
this plan was scoped under), not a departure from it: real per-command data showed 2 of the ~14
runnable `regex`-output commands use a shape the shared generic regex genuinely cannot parse at
all, while a dedicated small parser for each is cheap and now has real ground truth to test
against.

**Ruling:** treat `taplo`/`perlcritic` as linter-name-keyed special cases inside the same
`Output == "regex"` dispatch branch, falling back to the generic parser (below) for every other
`regex`-output linter. **Why:** a generic single-line regex cannot represent either format
(perlcritic's is key=value, not colon-separated; taplo's is multi-line) — forcing them through it
would silently produce zero or garbage findings. **Cost if wrong:** low — worst case, a future
follow-up swaps the special-case for something better; nothing downstream depends on the dispatch
mechanism being name-blind.

### Generic best-effort regex parser (remaining `regex`-output commands)

Applies to every other linter whose only runnable command has `Output: "regex"` and no other
blocker: `biome`, `djlint`, `dustilock`, `git-diff-check`, `markdownlint-cli2`, `rome`, `rumdl`,
`squawk` (its second, `--reporter Gcc`, command only — its first command uses an unsupported
`${linter}` var and is already `Skipped` by v0.3's existing logic, unchanged here), `stringslint`,
`swiftlint`, `ty`, `vale`, `yamllint`.

Of these, real samples/docs confirm the following fit a single-line `path:line[:col][: severity][:
[rule]] message` shape closely enough for one lenient parser:

- **yamllint** (`-f parsable`): `path:line:col: [level] message (rule-id)` — confirmed,
  yamllint's own docs.
- **git diff --check**: `path:line: error-type.` (no column, no rule; fixed message vocabulary) —
  confirmed via real sample.
- **vale** (`--output=line`): `path:line:col:message` — confirmed.
- **rumdl** (`rumdl check`): `path:line:col: [rule-id] message [fix-indicator]` — confirmed,
  rumdl's own docs.
- **markdownlint-cli2**: `path:line:col severity rule/rule-name message [Context: ...]` (space,
  not colon, after `col`) — **confirmed by direct local capture**: `npx markdownlint-cli2
bad.md` on a real broken-markdown fixture produced `bad.md:3:1 error MD010/no-hard-tabs Hard
tabs [Column: 1]` on stderr, matching this shape exactly.
- **swiftlint** (`--quiet`, default reporter): `path:line:col: severity: message (rule)` —
  moderate confidence (Xcode-compatible default format), not independently re-verified by running
  swiftlint locally (unavailable on this dev machine outside a real Swift toolchain).
- **squawk** (`--reporter Gcc`): `path:line:col: level: message` — GCC-format reporters are a
  well-known convention; moderate confidence, not independently re-run locally.

Real docs/samples confirm the following do **not** fit a single-line regex at all — the generic
parser will legitimately extract zero findings from their real output even when the tool found
real issues. This is a known, accepted limitation for this plan, not a bug to chase now:

- **biome** / **rome**: rich, multi-line code-frame diagnostics by default (confirmed via each
  tool's own docs/feature requests) — architecturally the same class of problem as taplo, but
  with no time budget to also reverse-engineer two more multi-line formats in this pass.
- **djlint**: its default line format has no per-line file path or column at all (grouped under a
  per-file header) — a single shared regex has nothing to anchor a `file`/`line` pair on.

No confirmed real sample exists for **ty**, **dustilock**, **stringslint** (per this plan's "never
fabricate a sample" rule) — they simply fall through the same generic parser as everything else;
in practice this likely yields zero findings for them too, same documented limitation as
biome/rome/djlint, not special-cased.

**Ruling:** ship the generic parser knowing it silently misses biome/rome/djlint/ty/dustilock/
stringslint's real findings (false negatives, not crashes — `check` reports "0 issues" for a
linter that actually found problems). **Why:** matching the approved v0.3.1 scope ("regex
générique best-effort"); a correct parser for each of these needs its own reverse-engineering pass
each roughly the size of the taplo/perlcritic work, which is out of this plan's approved budget.
**Cost if wrong:** a real false-negative silently under-reporting these ~6 linters until a
follow-up gives each its own parser — no crash, no data corruption, and the gap is explicitly
documented in code (a `ponytail:`-style comment on the generic parser) so it isn't mistaken for
full coverage.

## Non-goals (unchanged from v0.3, restated for this plan's boundary)

- `RunFrom`/`SandboxType`/unsupported-`${...}`-var linters remain `Skipped`, entirely out of this
  plan's scope (v0.3.2 candidate): `ansible-lint`, `brakeman`, `buf-breaking`, `buf-lint`,
  `clippy`, `detekt-gradle`, `golangci-lint`, `include-what-you-use`, `clang-tidy`, `mypy`,
  `cspell`, `dart`, `flake8`, `sourcery`, `shellcheck`, `terraform`, `tofu`, squawk's first
  command.
- `Command.Parser` (native-output-to-sarif converter scripts) is already `Skipped` since v0.3's
  final-review fix wave — unaffected by this plan.
- Formatter commands (`Formatter: true`) are still never run by `check` — unaffected.

## Architecture

All new parsers live in the existing `pkg/trunk/check/parse.go` (same file `ParseSARIF`/
`ParsePassFail` already live in — no new file, following that file's established shape: one
exported `ParseXxx(data []byte, linter string) ([]Finding, error)` per JSON format, or
`ParseXxx(data []byte, linter string) []Finding` where a parse failure isn't a real error, just "no
findings extracted," matching `ParsePassFail`'s existing no-error shape).

### New exported functions in `parse.go`

```go
func ParseActionlint(data []byte, linter string) ([]Finding, error)
func ParseBandit(data []byte, linter string) ([]Finding, error)
func ParseBuildifier(data []byte, linter string) ([]Finding, error)
func ParseCfnLint(data []byte, linter string) ([]Finding, error)
func ParseESLint(data []byte, linter string) ([]Finding, error)
func ParseHadolint(data []byte, linter string) ([]Finding, error)
func ParseHamlLint(data []byte, linter string) ([]Finding, error)
func ParseMarkdownlint(data []byte, linter string) ([]Finding, error)
func ParsePylint(data []byte, linter string) ([]Finding, error)
func ParseRubocop(data []byte, linter string) ([]Finding, error)
func ParseStylelint(data []byte, linter string) ([]Finding, error)
func ParsePerlCritic(data []byte, linter string) ([]Finding, error)
func ParseTaplo(data []byte, linter string) ([]Finding, error)
func ParseGenericRegex(data []byte, linter string) []Finding
```

Each populates the existing `Finding{Linter, File, Line, Column, Severity, RuleID, Message}` (no
`URL` — `ApplyIssueURL` is called uniformly afterward in `run.go`, unchanged). A schema field with
no equivalent (e.g. haml-lint has no column; buildifier/actionlint have no severity) is simply left
zero-valued — `Finding.Column == 0`/`Finding.Severity == ""` already mean "not reported," the same
convention `ParsePassFail` established in v0.3.

### `run.go` dispatch changes

The existing skip-condition chain in `runLinter` (RunFrom → SandboxType → unsupported var →
Output) is unchanged. Only the final "otherwise" branch's `Output` allow-check grows:

```go
switch cmd.Output {
case "sarif":
	findings, err = ParseSARIF(raw, linterName)
case "sarif_uri":
	findings, err = ParseSARIF(raw, linterName) // tmp_file already resolved the real SARIF bytes
case "pass_fail":
	// unchanged
case "actionlint":
	findings, err = ParseActionlint(raw, linterName)
case "bandit":
	findings, err = ParseBandit(raw, linterName)
case "buildifier":
	findings, err = ParseBuildifier(raw, linterName)
case "cfnlint":
	findings, err = ParseCfnLint(raw, linterName)
case "eslint":
	findings, err = ParseESLint(raw, linterName)
case "hadolint":
	findings, err = ParseHadolint(raw, linterName)
case "haml_lint":
	findings, err = ParseHamlLint(raw, linterName)
case "markdownlint":
	findings, err = ParseMarkdownlint(raw, linterName)
case "pylint":
	findings, err = ParsePylint(raw, linterName)
case "rubocop":
	findings, err = ParseRubocop(raw, linterName)
case "stylelint":
	findings, err = ParseStylelint(raw, linterName)
case "regex":
	switch linterName {
	case "perlcritic":
		findings, err = ParsePerlCritic(raw, linterName)
	case "taplo":
		findings, err = ParseTaplo(raw, linterName)
	default:
		findings = ParseGenericRegex(raw, linterName)
	}
default:
	// unchanged: Skipped, note naming the unsupported format
}
```

The `cmd.Output != "sarif" && cmd.Output != "pass_fail"` guard that currently gates entry into this
whole branch (the "otherwise Skipped" check earlier in `runLinter`) must grow to also allow every
new value above (`sarif_uri`, `actionlint`, `bandit`, `buildifier`, `cfnlint`, `eslint`, `hadolint`,
`haml_lint`, `markdownlint`, `pylint`, `rubocop`, `stylelint`, `regex`) — anything else remains
`Skipped` exactly as today.

## Testing approach (unchanged standing rule)

Every new `ParseXxx` gets its own test with a **real captured or source-verified sample** as input
(never a hand-invented one), asserting the exact resulting `[]Finding` — same standard as v0.3's
`ParseSARIF`/`ParsePassFail` tests. Where this plan's own research captured a real sample directly
(taplo, markdownlint-cli2), the task brief includes that literal captured text as the test fixture.
Where a format's schema was source/docs-verified but not locally re-captured (the 11 JSON formats,
perlcritic), the task brief includes a schema-accurate synthetic sample built from the verified
field names/nesting — not fabricated field names, but not a byte-for-byte tool transcript either;
this is consistent with v0.3's own `ParseSARIF` test, whose SARIF sample was hand-built from the
(fully public, standardized) SARIF schema rather than captured from a real tool run.

`run_test.go` gets new end-to-end cases (one fake-tool-binary linter per new dispatch branch,
mirroring v0.3's existing `fakesarif`/`fakepassfail` pattern) proving the dispatch switch actually
reaches each new parser, not just that the parser function works in isolation — the standing
"exact resulting behavior, not just no-error" lesson applies at both layers.

## Global constraints (carried into every task)

- No new `go.mod` dependencies — every new parser is plain `encoding/json` or manual string/regex
  parsing (`regexp`), no new third-party libraries.
- Every test asserts exact `Finding` values, never just "no error."
- Commits signed (`-S`), commitlint conventions per `.agents/skills/git-commit/SKILL.md`.
- `go build ./... && go vet ./... && go test ./... -count=1` clean before every task is done.
- Do not modify `match.go`, `run.go`'s skip-condition chain (RunFrom/SandboxType/var/Output-Skipped
  ordering), or any v0.3 CLI file (`internal/cli/check.go`) beyond wiring — this plan's entire
  surface is new `parse.go` functions plus `run.go`'s dispatch-switch extension.
