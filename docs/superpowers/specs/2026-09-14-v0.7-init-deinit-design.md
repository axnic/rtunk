# v0.7 — Init/Deinit: Design

**Status:** self-ruled (user granted full autonomy for v0.6+v0.7 via SDD; ground decisions in real
`trunk`'s behavior where relevant, self-rule where rtunk's own scope is deliberately narrower).

## Goal

Implement ROADMAP.md's v0.7 milestone: `rtunk init` (scaffold `.rtunk/` and its base config) and
`rtunk deinit` (reverse it).

## Ground truth from the real `trunk init`/`trunk deinit` (v1.25.0, installed on this machine)

`trunk init` is a substantial interactive wizard: repo-content detection (`--only-detected-
formatters`/`--only-detected-linters`), a `--lock` checksum mode, `--single-player-mode`
(gitignored config), `-y`/`-n` prompts, `--force` to overwrite. `trunk deinit` has one real flag,
`-y/--yes` ("proceed unconditionally" — implying an interactive confirmation prompt by default).

**rtunk's v0.7 is deliberately narrower**, matching the same "don't copy trunk's scope" pattern
v0.6 already established: ROADMAP.md's own wording is just "scaffold the `.rtunk/` configuration
directory and its base config" / "remove rtunk's configuration and any installed artifacts,
reversing `rtunk init`" — no detection wizard, no lock mode, no single-player mode. rtunk also has
zero interactive-prompt precedent anywhere in its existing CLI (every command so far is fully
scriptable/non-interactive, including `rtunk upgrade`'s own explicit non-goal of `-y`/`-n`
prompting) — `rtunk deinit` follows that same established precedent rather than trunk's own
default-interactive behavior: it just acts, no confirmation flag needed because there's nothing to
skip.

## A real, load-bearing gap found while researching this feature

**`internal/cli/findtrunk.go`'s `findTrunkYAML` only ever looks for `.trunk/trunk.yaml` — `.rtunk/
rtunk.yaml` is not read anywhere in the codebase today** (confirmed by that very function's own
doc comment: "rtunk's own `.rtunk/rtunk.yaml` is not read yet"). Every command (`check`, `fmt`,
`actions`, `git-hooks`, ...) calls this same function to locate its config file. If `rtunk init`
scaffolds `.rtunk/rtunk.yaml` without this being fixed, every other command still only ever finds
`.trunk/trunk.yaml` (or nothing) — the scaffolded file would be permanently invisible to the rest
of rtunk. This is not scope creep; it's a prerequisite this feature cannot skip. `findTrunkYAML`'s
own name is kept as-is (not renamed) despite now finding either file — a rename would touch every
call site in `internal/cli` for a purely cosmetic gain, and this codebase's own precedent (e.g.
`pkg/trunk/config`'s `Resolve` still means "read a trunk.yaml-shaped file" regardless of which
literal filename) treats "trunk.yaml" as the config concept's name, not a strict literal.

## Design

### `findTrunkYAML` (modified, `internal/cli/findtrunk.go`)

At each directory level walked upward (same git-root-bounded walk as today), check **`.rtunk/
rtunk.yaml` first, then `.trunk/trunk.yaml`**, at that same level, before moving up — so a
directory that has run `rtunk init` prefers its own native config over a legacy trunk one sitting
right next to it, while the nearest-directory-wins semantics (matching how git finds `.git`) are
unchanged from today. The two existing CLI-layer `repoRoot := filepath.Dir(filepath.Dir(configPath))`
assumptions (`check.go`/`fmt.go`, already flagged as a known pre-existing gap during v0.5's final
review, left untouched then as out of that branch's scope) still hold either way: both `.rtunk/
rtunk.yaml` and `.trunk/trunk.yaml` sit exactly two directories below repoRoot, so this rename-free
fix doesn't need to touch that separate, already-tracked issue.

### `rtunk init [--force]` (new, `internal/cli/init.go`)

Resolves `repoRoot` via the existing `gitRepoRoot(dir)` helper (already used by `git-hooks`/
`actions`, `internal/cli/githooks.go`) — this works even before any config exists (it only needs to
be inside a git repo, via `git rev-parse --show-toplevel`). Refuses to overwrite an existing
`<repoRoot>/.rtunk/rtunk.yaml` unless `--force` (matching real trunk's own `init --force`
semantics). Writes a minimal, valid scaffold:

```yaml
version: "0.1"
plugins:
  sources:
    - id: trunk
      uri: https://github.com/trunk-io/plugins
      ref: v1.11.0
```

`v1.11.0` is a real, currently-working `trunk-io/plugins` tag — the same one this repo's own real
`.trunk/trunk.yaml` already pins and this whole session has tested against all night, not an
arbitrary placeholder. Empty `enabled:` lists are intentionally omitted rather than written as
`[]`: `trunkFile`'s own struct fields already default to nil/empty when absent, so there is nothing
functionally different, and a shorter scaffold reads better as a starting point the user builds on
via the already-existing `rtunk check enable`/`rtunk actions enable`/`rtunk git-hooks install`.
Prints a short next-steps hint after writing.

`.rtunk/user.yaml` (AGENTS.md's own documented "git-ignored local override" concept) is **not**
scaffolded — `pkg/trunk/config`'s resolution pipeline doesn't implement any override-merging
behavior for it yet (a real, separate, undocumented-in-ROADMAP gap, out of scope here); creating an
unused empty file would be pure cargo-culting.

### `rtunk deinit` (new, `internal/cli/init.go`)

Resolves `repoRoot` the same way. If `<repoRoot>/.rtunk/` doesn't exist, prints "nothing to
deinit" and returns success (idempotent, matches this codebase's own established idempotency
convention — e.g. `check disable` on an already-absent id is a no-op, not an error). Otherwise:
removes `<repoRoot>/.rtunk/` entirely (`os.RemoveAll`), then calls the already-existing
`githooks.Uninstall(repoRoot)` (v0.5) to remove any rtunk-installed git hooks — "reversing `rtunk
init`" per ROADMAP.md's own wording means undoing everything `git-hooks install` (a separate,
already-shipped command any real init'd repo would have run) could have added, not just the config
file. Reports what was removed (the directory, and each hook name `githooks.Uninstall` returns).

## Testing strategy

- `findTrunkYAML`: table tests for the four real combinations (only `.rtunk/rtunk.yaml`, only
  `.trunk/trunk.yaml`, both present at the same level — `.rtunk/rtunk.yaml` wins, neither present
  at a nearer level but `.trunk/trunk.yaml` present at a farther one — still found, matching
  today's walk-upward behavior), plus the existing git-root-boundary test extended to cover both
  filenames.
- `rtunk init`: fresh repo (writes the exact scaffold content), already-initialized without
  `--force` (refuses, exact error), already-initialized with `--force` (overwrites), and an
  end-to-end round-trip proving the scaffolded file is actually readable afterward — run `rtunk
  init` then `rtunk check list` (or any other already-shipped command) against the same repo with
  no `--config` flag and assert it resolves the freshly-scaffolded config, the direct proof the
  `findTrunkYAML` fix actually closes the gap this spec opened with.
- `rtunk deinit`: removes an existing `.rtunk/` (exact directory-gone assertion), removes installed
  git hooks (real temp git repo, install via `git-hooks install` first, then `deinit`, assert the
  hook files are gone — reusing `pkg/trunk/githooks`'s own already-established real-git-repo test
  pattern), and the no-op case (never initialized, exits 0, exact message).

## Non-goals (ruled, disclosed)

- No repo-content detection / `--only-detected-*` wizard.
- No `--lock` checksum mode (matches AGENTS.md/session's already-made "postpone --secure/signature
  verification to v1+" decision).
- No `--single-player-mode` (gitignored local config variant).
- No interactive confirmation prompt on `deinit` — consistent with rtunk's zero interactive-prompt
  precedent everywhere else (established explicitly for `rtunk upgrade` in v0.6, extended here).
- `.rtunk/user.yaml` is not scaffolded and its override-merging behavior is not implemented — a
  real, separate, pre-existing gap in `pkg/trunk/config`, out of scope for this feature.
- `findTrunkYAML` is not renamed despite now covering two filenames — minimizes diff surface across
  every `internal/cli` call site for a purely cosmetic gain.
