# v0.9.2 `--format human|sarif|json`: Design

**Status:** design agreed with the user in conversation (2026-09-26) before this spec was written.
This is sub-project 2 of 4 of ROADMAP `v0.9`; see Scope.

## Scope

ROADMAP `v0.9` ("Output and UX", [ROADMAP.md](../../../ROADMAP.md), [docs/ux.md](../../ux.md)) is
decomposed into four sub-projects, each with its own spec and plan:

1. Event stream + plain renderer
   ([v0.9.1 spec](./2026-09-26-v0.9.1-event-stream-plain-renderer-design.md), implemented).
2. **`--format human|sarif|json` on `check` and `fmt`** (this spec).
3. TTY live view.
4. Filtered `linters list` / `actions list`.

This spec covers only #2. It builds directly on the v0.9.1 renderer seam
(`internal/cli/render`): every format is a `Renderer` over the same event stream, and they differ
only in `Close`.

## Goal

`check` and `fmt` gain `--format human|sarif|json` (default `human`).

- `human` is the v0.9.1 plain report, renamed, plus color when stdout is a TTY. Non-TTY output is
  byte-identical to v0.9.1.
- `json` is one stable JSON document on stdout, for machine consumers (`check` and `fmt`).
- `sarif` is one SARIF 2.1.0 document on stdout, for CI code-scanning uploads (`check` only).
- Progress lines stay on stderr for every format; stdout carries only the report or document.
- Exit codes are unchanged for every format.

## Current state

- `internal/cli/render/render.go` defines `Renderer` (`Event`, `Close(Summary)`), `Options{Command,
NoProgress, NoColor}`, `Summary{Elapsed, RunLog, Skipped, Changed, Unstable}` and
  `NoColorFromEnv()`.
- `internal/cli/render/plain.go` holds one implementation, `plain` (`NewPlain`). It mixes three
  concerns in one type: collection state (`findings`, `failed`/`failedSeen`, `files`, `linters`),
  the stderr progress line written in `Event`, and the human text written in `Close`
  (`writeIssues`, `writeChanged`, `writeFailures`, `severity`, `plural`). It emits no color;
  `Options.NoColor` is stored and unused.
- `internal/cli/check.go` (`checkRunCmd.Run`) and `internal/cli/fmt.go` (`fmtCmd.Run`) call
  `render.NewPlain(stdout, stderr, render.Options{Command, NoProgress, NoColor:
render.NoColorFromEnv()})` directly. `check --fix` builds a second `render.Fmt` instance for the
  formatter pass, closed before the checking pass runs, so a `--fix` run writes two reports to
  stdout today.
- Neither command has `--format`. docs/cli.md ("Output") and ROADMAP.md (v0.9 item 2) list it as
  planned; docs/ux.md says color is not implemented.
- `pkg/trunk/output` already fixes the vocabulary: `Finding{Linter, File, Line, Column, Severity
("error"|"warning"|"info"), RuleID, Message, URL}` (`finding.go`). `ParseSARIF`
  (`sarif.go`) reads `runs[].results[]` with `ruleId`, `level`, `message.text` and
  `locations[0].physicalLocation` (`artifactLocation.uri`, `region.startLine|startColumn`), maps
  `error|warning` to themselves and anything else to `info`. The emitted document mirrors that
  shape in the other direction.
- The rtunk version is `internal/cli.Version` (`internal/cli/cli.go`, `var Version = "dev"`,
  set by `cmd/rtunk/main.go`). `render` cannot import `internal/cli` (import cycle), so the
  version reaches the SARIF renderer through `Options`.
- Sorting, severity mapping and failure de-duplication live in `plain.go`
  (`writeIssues`, `severity`, `Event`); JSON and SARIF need the same data, in the same order.

## Design

### 1. Shared base

Extract from `plain` a `base` struct embedded by the `human`, `json` and `sarif` renderers:

```go
type base struct {
    stdout, stderr io.Writer
    opts           Options

    findings   []output.Finding // Linter back-filled from the event, as today
    failures   []failure        // {Linter, Err string}: first Failed event per linter, arrival order
    failedSeen map[string]bool
    files      map[string]bool  // unique files across terminal events
    linters    map[string]bool  // linters that emitted a terminal event
}

func (b *base) Event(ev engine.Event) // collection + the stderr progress line; identical to plain.Event
func (b *base) sortedFindings() []output.Finding // file, line, column (stable), today's writeIssues order
func (b *base) sortedFailures() []failure        // by linter name
```

- `base.Event` is `plain.Event` moved verbatim (`Running` dropped, findings collected, the
  progress line written to `stderr` unless `NoProgress`); `doneDetail` and `failureText` move with
  it. The progress line is the same for all three formats.
- `failure.Err` is `failureText(ev)` (first line of the error, or the note). It is retained so the
  JSON `failures[].error` and the SARIF notification message carry the cause; the human report
  still prints only `failed to run` plus the log uid.
- The severity mapping (`severity`), `plural` and the human writers stay in `human.go`.
- Each renderer type is `struct{ base }` (or `base` plus renderer-specific fields) and implements
  only `Close`. No behavior lives in `base` beyond collection and ordering, consistent with the
  v0.9.1 rule that renderers hold presentation state only.

Files after the refactor: `render.go` (types, `New`), `base.go`, `human.go` (was `plain.go`),
`color.go`, `json.go`, `sarif.go`.

### 2. Constructor and options

```go
type Format int

const (
    Human Format = iota
    JSON
    SARIF
)

type Options struct {
    Format     Format // Human (zero value), JSON, SARIF
    Command    Kind
    NoProgress bool
    Color      bool   // human only: emit ANSI color; computed by the CLI, see section 3
    Version    string // SARIF tool.driver.version; the CLI passes internal/cli.Version
}

func New(stdout, stderr io.Writer, opts Options) Renderer // switch on opts.Format
```

- `NewPlain` disappears; `render.New` replaces it at the three call sites (`check.go` twice,
  `fmt.go` once). `Options.NoColor` is replaced by `Options.Color` (the positive form is what the
  renderer needs; the decision is made once in the CLI, see below). `NoColorFromEnv` is removed
  when its last caller goes.
- `Format` zero value is `Human`, so a caller that sets no format keeps v0.9.1 behavior.
- The renderers only ever see the resolved decision; they read no environment and no file
  descriptor. This keeps them pure functions of (events, `Summary`, `Options`).

### 3. `human`: rename plus color

`human` is `plain` renamed, with the same layout as v0.9.1 (headers, blocks, `FAILURES`, `Skipped`,
`Checked ... in Ts`, verdict; unchanged wording). Color is the only addition.

**Decision.** A pure function in `internal/cli/render`:

```go
// UseColor reports whether ANSI color is allowed: stdout is a terminal and NO_COLOR is empty.
func UseColor(isTTY bool, noColor string) bool { return isTTY && noColor == "" }
```

The CLI computes `UseColor(isTerminal(stdout), os.Getenv("NO_COLOR"))` once per command and puts the
result in `Options.Color`. `isTerminal` is a small helper in `internal/cli`: `stdout` is an
`*os.File` and `f.Stat()` reports `ModeCharDevice`; anything else (a `bytes.Buffer` in tests, a
pipe, a file) is `false`. Stdlib only. `golang.org/x/term` is deliberately not added yet: docs/ux.md
plans it for sub-project #3, which needs the terminal width, and this sub-project does not.

`ModeCharDevice` is also true for `/dev/null`; that is accepted (color escapes to `/dev/null` are
harmless) and noted as a known imprecision fixed when `x/term` arrives in #3.

**Palette** (docs/ux.md "Issues output"; escapes applied by `human` only when `Options.Color`):

| Element                                    | Style                |
| ------------------------------------------ | -------------------- |
| File header path in the `ISSUES` blocks    | bold                 |
| Issue severity word, `high`                | red                  |
| Issue severity word, `medium`              | yellow               |
| Issue severity word, `low`                 | dim                  |
| `linter/rule` at the end of the issue line | dim                  |
| Verdict glyph and text: failing verdict    | red; passing verdict | green |
| `FAILURES` header and `✖` on failure lines | red                  |

- The words `high|medium|low` are always printed; color never carries information alone, matching
  docs/ux.md. The severity glyphs `✖ ▲ ·` in front of the word in issue lines (docs/ux.md) are
  added only when `Options.Color` is set; the non-TTY layout keeps the v0.9.1 word-only issue
  line, which is what makes non-TTY output byte-identical.
- Escapes are the SGR sequences `\x1b[1m` (bold), `\x1b[2m` (dim), `\x1b[31m|32m|33m` and `\x1b[0m`
  (reset), written by a tiny helper `paint(color bool, code, s string) string` in `color.go`. When
  `color` is false it returns `s` unchanged, so the plain path has no branches beyond that call.
- Column alignment is computed on the uncolored text: padding is applied before painting so escapes
  do not shift the columns.
- The stderr progress lines are not colored in this sub-project (stderr is a different file
  descriptor whose TTY state is not checked here); the TTY live view (#3) owns colored progress.

`--format` defaults to `human` regardless of TTY, so a piped or redirected run is the v0.9.1 output
byte for byte. The TTY live view (#3) will extend `human`; it does not add a fourth format.

### 4. `--format json`

One JSON document on stdout, written by `Close`, indented with two spaces and terminated by a
newline. Progress lines stay on stderr (`--no-progress` silences them); stdout is only the document.

```json
{
  "version": 1,
  "command": "check",
  "elapsed_ms": 14213,
  "run_log": "3f9a2c",
  "files_checked": 232,
  "linters": 6,
  "issues": [
    {
      "file": "pkg/trunk/download/shim.go",
      "line": 57,
      "column": 3,
      "severity": "high",
      "message": "QF1012: Use fmt.Fprintf(...) instead of ...",
      "linter": "golangci-lint2",
      "rule": "staticcheck",
      "url": ""
    }
  ],
  "failures": [{ "linter": "gitleaks", "error": "exit status 2" }],
  "skipped": ["shfmt [unsupported output format \"x\"]"],
  "changed": []
}
```

- `version` is the schema version of this document (integer `1`), not the rtunk version. It is bumped
  only on a breaking change to the shape.
- `command` is `"check"` for `Kind` `Check` and `"fmt"` for `Fmt` and `FmtCheck`. `--check` is not a
  separate command value: the caller distinguishes it by `changed` meaning "would be reformatted"
  (the invocation is the caller's own).
- `elapsed_ms` is `Summary.Elapsed` in whole milliseconds; `run_log` is `Summary.RunLog` (`""` when
  logging is disabled, always present); `files_checked` and `linters` are `len(base.files)` and
  `len(base.linters)`, the same counts as the human footer.
- `issues` is sorted by file, then line, then column (`sortedFindings`, same order as the human
  report; stable for ties). Each issue: `file` repoRoot-relative as the engine reports it; `line` and
  `column` integers (`0` when the linter reports none, unlike SARIF which omits them); `severity` is
  `high|medium|low` via the same `severity()` mapping as `human`; `message`, `linter`, `rule`
  (`Finding.RuleID`, `""` when none) and `url` (`Finding.URL`, `""` when none). All keys are always
  present. `url` is printed here for the first time (v0.9.1 dropped it from the text report).
- `failures` is one entry per failed linter (first `Failed` event per linter), sorted by linter name,
  `error` being the first line of the error text as in the stderr progress line.
- `skipped` is `Summary.Skipped` verbatim (`"linter [note]"`).
- `changed` is `Summary.Changed`, deduplicated and sorted (as `writeChanged` does). For `fmt` these
  are the files reformatted, or, with `--check`, the files that would be. For `check` it is empty,
  except under `check --fix` (section 6).
- Empty collections are `[]`, never `null` (slices are initialized non-nil before encoding).
- `fmt`: `issues` is `[]` (a formatter command has no findings); `failures`, `skipped`, `changed`
  as above.
- The document is encoded with `encoding/json` from unexported structs with explicit tags; no
  `omitempty` anywhere, so the key set is constant. HTML escaping is disabled
  (`Encoder.SetEscapeHTML(false)`) so messages containing `<`, `>` and `&` stay readable.

### 5. `--format sarif`

SARIF 2.1.0, written by `Close` with the same encoder settings as `json`. Supported on `check`
only (see section 6 for `fmt`).

```json
{
  "$schema": "https://json.schemastore.org/sarif-2.1.0.json",
  "version": "2.1.0",
  "runs": [
    {
      "tool": {
        "driver": {
          "name": "rtunk",
          "version": "v0.9.2",
          "rules": [{ "id": "golangci-lint2/staticcheck" }]
        }
      },
      "invocations": [
        {
          "executionSuccessful": false,
          "toolExecutionNotifications": [{ "level": "error", "message": { "text": "gitleaks: exit status 2" } }]
        }
      ],
      "results": [
        {
          "ruleId": "golangci-lint2/staticcheck",
          "level": "error",
          "message": { "text": "QF1012: Use fmt.Fprintf(...) instead of ..." },
          "locations": [
            {
              "physicalLocation": {
                "artifactLocation": { "uri": "pkg/trunk/download/shim.go" },
                "region": { "startLine": 57, "startColumn": 3 }
              }
            }
          ]
        }
      ]
    }
  ]
}
```

- `$schema` is the fixed URL above and `version` is `"2.1.0"`. The URL is only a string in the
  document; nothing fetches it.
- `runs` has exactly one run. `tool.driver.name` is `"rtunk"`, `tool.driver.version` is
  `Options.Version` (the CLI passes `internal/cli.Version`, which is `"dev"` in an unstamped build).
- `tool.driver.rules` is the deduplicated set of rule ids of the issues, in the order of the sorted
  issues, each `{"id": <ruleId>}`. A rule id is `linter/rule`, or `linter` alone when
  `Finding.RuleID` is empty (the same `src` string `human` prints). `rules` is `[]` when there is no
  issue. When the finding carries a `URL`, the rule gets `"helpUri": "<url>"` (first URL seen for
  that id wins).
- `results` has one entry per issue, in the sorted issue order, so `len(results)` equals the number
  of issues (`[]` when none).
  - `ruleId`: the same `linter/rule` string as `rules[].id`.
  - `level`: `error` for `error`, `warning` for `warning`, `note` for `info` (and for any unknown
    severity, mirroring the `low` default). This is the inverse of `sarifSeverity` in
    `pkg/trunk/output/sarif.go`.
  - `message.text`: `Finding.Message`.
  - `locations[0].physicalLocation.artifactLocation.uri`: the repoRoot-relative path as reported
    (forward slashes, no `file://`; `ParseSARIF` trims `file://` on input, and a relative uri
    resolves against the repository root in SARIF consumers). `region.startLine` and
    `region.startColumn` are written only when greater than `0`; when `line` is `0` the `region`
    object is omitted entirely (SARIF requires `startLine >= 1`).
- `invocations[0]`: `executionSuccessful` is `false` when at least one linter failed, `true`
  otherwise; `toolExecutionNotifications` has one entry per failed linter (sorted by linter name),
  `level: "error"`, `message.text` `"<linter>: <error>"`. The array is `[]` when there is no
  failure. Skipped linters are not represented (no SARIF construct fits; they remain on stderr and
  in `json`). `executionSuccessful` describes only whether the linters ran; it does not encode
  findings (SARIF convention: findings are results, not execution failures).
- `Summary.Elapsed`, `RunLog`, file and linter counts have no SARIF equivalent and are omitted.

### 6. `fmt` and `--fix` under the machine formats

- **`fmt --format json`** is supported: `command: "fmt"`, `issues: []`, `changed` lists the files
  reformatted, or the files that would be reformatted with `--check`. `--verify-stable` emits the
  document once, after both rounds, from the merged `changed` (as the human report does, per
  v0.9.1 section 2); an unstable result still returns `unstableFormatError`.
- **`fmt --format sarif` is refused.** SARIF has no faithful representation of "files rewritten"
  (results describe defects at locations), so rtunk does not invent one. `fmtCmd.Run` rejects it
  before any file selection, linter resolution or engine run, with the usage error
  `rtunk: --format sarif is only supported by check` and exit code `1` (any returned error exits
  `1`, `cmd/rtunk/main.go`). Nothing is written to stdout, nothing is executed, no run log is
  started, no file is written. The check sits at the top of `Run`, before `findTrunkYAML`, so it
  fires regardless of repository state.
- **`check --fix`** runs a formatter pass, then the checking pass. Two documents on one stdout would
  not parse, so the formatter pass is rendered as its own report only when the format is `human`
  (unchanged v0.9.1 behavior: formatter report, then check report). For `json` and `sarif`,
  `check --fix` emits exactly one document, for the checking pass:
  - the formatter pass still runs, still streams its progress lines to stderr, and still counts
    toward the exit code (`fixFailed`, `runFailed`); it just has no stdout renderer of its own. In
    `check.go` it is fed a stderr-only path: its events go to a `render.Fmt` renderer built with the
    `Human` format whose `stdout` is `io.Discard` (progress lines are written to the real stderr
    unless `--no-progress`), and its `Close` output is dropped.
  - its changed files (`changed`, `fixSkipped`) are passed to the check renderer's `Summary`: for
    `json` they become `changed` (and its skipped linters are merged into `skipped`, deduplicated);
    `Summary.Changed` is otherwise empty for `check`.
  - for `sarif` there is no place for them: the SARIF document covers the check pass only, and the
    formatter pass's changed files are not represented (they remain visible on stderr).
  - `files_checked` and `linters` in `json` count the checking pass only (events the check renderer
    saw).
- `check --format sarif --fix` is therefore allowed; only `fmt --format sarif` is refused.

### 7. CLI flag and wiring

- `check` (`checkRunCmd`) and `fmt` (`fmtCmd`) gain
  `Format string \`enum:"human,sarif,json" default:"human" help:"Output format."\``. Kong validates
the enum: an unknown value is a usage error (exit `1`, kong's message listing the allowed values)
before `Run` executes. The flag name, values and default are the ones in docs/cli.md "Output".
- Both commands map `c.Format` to `render.Format` (a five-line switch shared in `internal/cli`),
  compute `Options.Color` per section 3, pass `Options.Version = Version`, and call `render.New`.
- `drainRunEvents` and `collectChangedByLinter` are unchanged; they still take `r.Event` and return
  what the exit-code logic needs.
- `warnIfRecentOverlap`, `rtunk: no files to check|format`, `skipPartiallyStaged` warnings and the
  log warning stay on stderr under every format. They are not progress lines and `--no-progress`
  does not suppress them (v0.9.1 rule, unchanged). The early return on "no files" writes no
  document: with `--format json|sarif` and no selected files, stdout is empty and the exit code is
  `0`, as in v0.9.1 (consumers must treat empty stdout plus exit `0` as "nothing ran"). Emitting an
  empty document there is deliberately not done, to avoid changing the early-return contract in
  this sub-project; see Open questions.
- Exit codes are unchanged for every format: `1` on findings (`rtunk: check found N issue(s)`), a
  failed linter, `fmt --check` with files to reformat, `unstableFormatError`; `0` otherwise. The
  error text is returned to `cmd/rtunk/main.go` and printed on stderr exactly as today, so with
  `--format json|sarif` stdout is still only the document.

### 8. Documentation touched by the implementation plan

Not this spec's edits: docs/cli.md ("Output": `--format` implemented, `check` and `fmt` synopsis,
`sarif` unsupported on `fmt`), docs/ux.md (color implemented, palette, implementation status),
ROADMAP.md (v0.9 item 2 marked implemented, `human` default wording: default is `human` always, not
"on a TTY"), and the `render` package comment.

## Non-goals

- Validating the emitted SARIF against the official JSON schema (no dependency, no network); tests
  assert structure only.
- SARIF for `fmt` (refused, see section 6), or any representation of formatter changes in SARIF.
- `--format` on other commands (`linters list --format json` belongs to sub-project #4).
- Color themes, configurable palettes, colored stderr progress.
- The TTY live view (#3), `golang.org/x/term` and terminal width handling.
- Emitting a document when nothing ran (the "no files" early return).
- Changing `output.Finding`, the run-log schema, file selection or exit codes.
- Documented stability guarantees for the `json` schema beyond `version: 1`.

## Testing

- **Renderer golden tests** (`internal/cli/render`, table-driven, synthetic `[]engine.Event` plus a
  `Summary`, stdout and stderr asserted separately), JSON and SARIF as golden files under
  `internal/cli/render/testdata/`:
  - `json`: findings across several files (sort by file/line/column, severity mapping, empty
    `RuleID`, `url` set and empty), failures with and without `RunLog`, skipped, fmt `changed`, fmt
    `--check`, clean run (all arrays `[]`, never `null`), `--verify-stable` merged changed, HTML
    characters in a message are not escaped;
  - `sarif`: same event streams for `check`, asserting `results` order, level mapping
    (`error|warning|info` to `error|warning|note`), `region` omitted when `line` is `0`,
    `startColumn` omitted when `0`, `helpUri` from `URL`, `executionSuccessful` false with
    notifications on failure and true on a clean run;
  - structural SARIF assertions by decoding into a `map[string]any`: `version == "2.1.0"`,
    `$schema` present, exactly one run, `len(runs[0].results)` equals the issue count,
    `tool.driver.rules` ids unique and each result's `ruleId` present in them, `tool.driver.name ==
"rtunk"`, `tool.driver.version == Options.Version`;
  - `human`: existing v0.9.1 golden tests carry over unchanged after the rename (same bytes with
    `Color: false`); with `Color: true` a golden containing the SGR sequences and the severity
    glyphs, and assertions that the severity words are still present and columns align on the
    uncolored text;
  - progress lines identical across the three formats for the same events; `NoProgress` silences
    all three; `Running` events never printed.
- **Color decision** (`render`): `UseColor` as a pure function, table over `(isTTY, noColor)`:
  color only for `(true, "")`; `NO_COLOR=1` or any non-empty value disables it; empty string does
  not.
- **CLI tests** (`internal/cli`):
  - `--format json`: stdout parses as exactly ONE JSON document (`json.Decoder` reads one value and
    then `io.EOF`), stderr still carries one progress line per finished linter, and none with
    `--no-progress`;
  - `--format sarif` on `check`: stdout parses as one document, `runs[0].results` length matches the
    findings;
  - human output unchanged when stdout is not a TTY (buffer): no `\x1b` bytes, and the bytes equal
    the v0.9.1 goldens;
  - unknown `--format` (`--format xml`) is rejected by Kong as a usage error before any linter
    runs, with a non-zero exit;
  - `fmt --format sarif` returns the `--format sarif is only supported by check` error and exit
    code `1` without running any linter and without writing any file or stdout byte (assert the
    engine is never invoked, no run log is created, and the working tree is untouched);
  - `fmt --format json` (`changed` populated) and `fmt --check --format json` (`changed` lists
    would-be files, exit `1` when non-empty);
  - `check --fix --format json` emits one document with the formatter pass's files under
    `changed`; `check --fix --format sarif` emits one document; `check --fix` in human still
    prints the formatter report then the check report;
  - exit codes for `json` and `sarif` on findings (`1`), on a failed linter (`1`, failure present in
    the document), clean run (`0`), all unchanged from `human`.

## Open questions

- Exact JSON field naming details (for example `elapsed_ms` versus `elapsed`, the shape of
  `failures[]`) are fixed by the golden tests, not by this spec.
- A run that selects no files writes no document under `json|sarif` (empty stdout, exit `0`, see
  section 7). Whether a machine-format consumer should instead receive an empty document there is
  left to the golden-test round; the default here is to keep the v0.9.1 early-return contract.
