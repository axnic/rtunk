# `rtunk check` v0.3.2 — RunFrom / SandboxType Support — Design Spec

## Goal

v0.3's design spec explicitly deferred `Command.RunFrom` and `Command.SandboxType`: any command
with either field set is `Skipped`, regardless of its `Output` format. v0.3.1 closed the output-
format gap but left this one exactly as documented. This plan implements both fields so the
linters that need them actually run, closing rtunk's last major "silently skipped" category from
the real trunk-io catalog.

## Scoping method

Surveyed every command's `RunFrom`/`SandboxType`/`Run` string across the real trunk-io plugin
catalog (`~/Library/Caches/rtunk/plugins/*.json`, 129 linters, 198 commands), grouping by the
distinct values found and cross-referencing each against `Command.Batch`, `Command.DirectConfigs`
(via the owning `Linter`), and any other already-known skip condition (unsupported `${...}` var).

## Scope: in this plan

### `RunFrom` (26 commands)

| Form                                  | Count | Resolution                                                                                       | Real examples                                                                                                                                                                                              |
| ------------------------------------- | ----- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `""` (empty)                          | 172   | repoRoot (unchanged)                                                                             | most linters                                                                                                                                                                                               |
| `${parent}`                           | 6     | repoRoot — see reasoning below                                                                   | ansible-lint, dart (`analyze`), flake8, snyk, yamlfmt                                                                                                                                                      |
| `${target_directory}`                 | 6     | `dirname(target)`                                                                                | brakeman, clippy, terraform, tfsec, tofu, tflint (1 of 2)                                                                                                                                                  |
| `${root_or_parent_with(FILE)}`        | 8     | walk up from `dirname(target)` to repoRoot inclusive; first dir containing `FILE`; else repoRoot | golangci-lint + golangci-lint2 (`go.mod`, 1 each), scalafmt (`.scalafmt.conf`), tflint (`.tflint.hcl`), dart (`analysis_options.yaml`, ×2 commands), buf-lint (`buf.yaml`), buf-breaking (`buf.work.yaml`) |
| `${root_or_parent_with_regex(REGEX)}` | 1     | same walk; first dir containing a file matching `REGEX`                                          | dotnet-format (`(.+\.csproj)` or `(.+\.sln)`)                                                                                                                                                              |
| `${root_or_parent_with_any_config}`   | 2     | same walk; first dir containing any of the owning `Linter.DirectConfigs`                         | mypy (`DirectConfigs: [mypy.ini, .mypy.ini]`)                                                                                                                                                              |
| `${compile_command}`                  | 2     | **not implemented** — deferred, see Non-goals                                                    | clang-tidy, include-what-you-use                                                                                                                                                                           |
| `apps` (bare literal, no `${...}`)    | 1     | **not implemented** — unrecognized literal, `Skipped` like any future unknown value              | brakeman (second command)                                                                                                                                                                                  |

**`${parent}` reasoning (inference, no official doc exists — trunk's engine is closed-source):**
every real command using it (ansible-lint, dart analyze, flake8, snyk, yamlfmt) is a tool that
needs project-root context to resolve relative references (roles, imports, package layout), not
file-local context. Real trunk supports nested workspaces (a sub-project with its own
`.trunk/trunk.yaml` inside a larger repo), where `${parent}` most plausibly means "run from the
parent workspace's root" — a concept this project's `config.Config` doesn't model yet (one
`trunk.yaml` resolves to one flat config). In a single-workspace model, "the parent workspace"
degenerates to repoRoot, which is also already the default when `RunFrom` is empty. This is a
defensible degenerate case for the scope rtunk currently supports, not a guess in the dark: if
rtunk ever adds nested-workspace support, `${parent}`'s resolution is the one thing that would need
to change, in one place (`runfrom.go`).

### `SandboxType` (12 commands)

| Value          | Count | Behavior                                                                                                                                                    | Real examples                                                                                       |
| -------------- | ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `""` (empty)   | 186   | run directly against real files (unchanged)                                                                                                                 | most linters                                                                                        |
| `copy_targets` | 10    | copy only the matched target file(s) into an isolated temp dir, preserving their path relative to the resolved `RunFrom` directory (or repoRoot); run there | cspell, gitleaks, remark-lint, semgrep, shellcheck, terragrunt (×2), trufflehog, buf-breaking, snyk |
| `expanded`     | 2     | **inferred, not documented** — copy every regular file directly inside the resolved directory (non-recursive), not just the matched targets; run there      | gokart, tflint (1 of 2)                                                                             |

**`expanded` reasoning (inference):** both real uses (gokart scanning a Go package, tflint
validating a Terraform module) need sibling-file context a single isolated target file wouldn't
provide — Go packages and Terraform modules are conventionally single-directory units. No real
command combines `expanded` with `copy_targets`, consistent with them being two alternative staging
strategies rather than a spectrum. Flagged in code as a best-effort interpretation with a
`ponytail:`-style comment, same as v0.3.1 treated its own inferred schemas.

**Refinement found during plan-writing:** `gokart`'s real command leaves `RunFrom` empty while
setting `SandboxType: expanded` — under this spec's plain resolution rules that would default to
repoRoot, which "expands" nothing meaningful for a per-file-context tool. `tflint`'s own `expanded`
command instead sets `RunFrom: ${target_directory}` explicitly. The implementation plan resolves
this by defaulting `RunFrom` to `${target_directory}` specifically when `SandboxType == "expanded"`
and `RunFrom` is otherwise empty (an explicit `RunFrom` of any form, including `${parent}`, is left
untouched) — see the plan's `buildJobs` for the exact rule.

### Combining `RunFrom` and `SandboxType`

Two real commands set both: `snyk` (`${parent}` + `copy_targets`) and `buf-breaking`
(`${root_or_parent_with(buf.work.yaml)}` + `copy_targets`). `buf-breaking`'s `Run` string also
contains `${upstream-ref}`, already unsupported by v0.3's template-var allowlist — implementing
this plan does not newly unlock `buf-breaking`, only `snyk`. The two features are still implemented
as fully composable (a resolved `RunFrom` directory becomes the sandbox's staging root when both
are set), not a `snyk`-specific special case — the mechanism is general even though only one real
command currently exercises the combination.

### Real impact: what this plan actually unlocks

Cross-referencing every `RunFrom`/`SandboxType` command above against v0.3/v0.3.1's already-shipped
`Output`-format allowlist, `Parser`, and `Formatter` checks: most of the 38 commands surveyed remain
`Skipped` after this plan too, blocked by a _different_, already-documented non-goal. Only these
newly run:

| Linter         | Command                | Feature this plan adds                                                                                         |
| -------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| brakeman       | `lint`                 | `RunFrom: ${target_directory}`                                                                                 |
| dart           | `analyze`              | `RunFrom: ${parent}`                                                                                           |
| flake8         | `lint`                 | `RunFrom: ${parent}`                                                                                           |
| golangci-lint2 | `lint`                 | `RunFrom: ${root_or_parent_with(go.mod)}`                                                                      |
| cspell         | `lint`                 | `SandboxType: copy_targets`                                                                                    |
| gitleaks       | `lint`                 | `SandboxType: copy_targets`                                                                                    |
| semgrep        | `check`                | `SandboxType: copy_targets`                                                                                    |
| gokart         | `lint`                 | `SandboxType: expanded`                                                                                        |
| tflint         | `lint` (both commands) | `RunFrom: ${target_directory}`/`${root_or_parent_with(.tflint.hcl)}` + `SandboxType: expanded` (first command) |

9 linters, 10 commands. Everything else surveyed remains `Skipped` for a separate reason already
documented as a v0.3/v0.3.1 non-goal — mostly an `Output` value this project doesn't parse yet
(`ansible_lint`, `brakeman`, `buf`, `clippy`, `golangci_lint`, `mypy`, `shellcheck`,
`terraform_validate`, `llvm` — candidates for a future "second wave of output formats" plan), plus a
few `Command.Parser` cases (`remark-lint`, `tfsec`, `trufflehog`) and formatter-only commands
(`dart format`/`fix`, `dotnet-format`, `scalafmt`, `terragrunt format`, `yamlfmt` — `check` never
runs these regardless, per v0.3's own Formatter rule). This plan is still worth shipping on its own
merits — it closes the _entire_ `RunFrom`/`SandboxType` gap, a real and durable piece of technical
debt — but its immediate visible effect on `rtunk check`'s output is these 9 linters, not all 38
commands surveyed.

`ansible-lint` and `snyk` both set a `RunFrom`/`SandboxType` this plan resolves correctly, but
neither actually runs: both have an empty/null `Linter.Files` in the real catalog — a separate,
pre-existing gap unrelated to `RunFrom`/`SandboxType` (`check.Files()` returns before either field
is ever consulted, see its early `if len(linter.Files) == 0 { return nil, nil }`) — so they're
excluded from the table above. This also means `snyk`, the only real command combining `RunFrom`
and `SandboxType` (see below), currently has zero live-catalog exercise of that combination; it's
still correctly implemented and covered end-to-end by the fake `combo-linter` test in
`run_test.go`, just worth stating plainly rather than implying `snyk` itself proves it out.

## Non-goals (explicit, ruled during brainstorming)

- **`${compile_command}`** (clang-tidy, include-what-you-use): both commands' `Run` strings also
  reference `${compile_commands_dir}` (clang-tidy) or embed `${compile_command}` as a Run-string
  substitution, not just a `RunFrom` value (include-what-you-use) — this requires parsing a
  `compile_commands.json` compilation database and a wholly new template-var substitution, an
  independent C/C++-specific subsystem unrelated to directory resolution. Explicitly deferred to a
  future plan if ever prioritized.
- **The literal `RunFrom: "apps"` value** (brakeman): not a recognized template form, one command,
  no generalizable pattern. Falls through to `Skipped` like any future unrecognized value.
- **New template vars beyond `${target}`/`${tmpfile}`**: unaffected by this plan. A command whose
  `Run` string uses an unsupported var stays `Skipped` regardless of `RunFrom`/`SandboxType`
  support (e.g. `buf-breaking`, `squawk`'s first command).
- **Nested/multi-workspace `trunk.yaml` support**: out of scope; `${parent}`'s resolution assumes
  today's single-workspace model (see reasoning above).

## Architecture

Two new files in `pkg/trunk/check/`, plus integration changes in `run.go`.

### `runfrom.go`

```go
// resolvedRunFrom is what one matched file resolves RunFrom to: the absolute directory a command
// invocation should run from, given that file. Files sharing the same resolvedRunFrom are grouped
// into the same invocation (see run.go's buildJobs changes).
func resolveRunFrom(runFrom, target, repoRoot string, directConfigs []string) (dir string, ok bool)
```

- `runFrom == ""` or `"${parent}"` → `(repoRoot, true)`.
- `"${target_directory}"` → `(filepath.Dir(target), true)`.
- `` `${root_or_parent_with(...)}` `` / `` `${root_or_parent_with_regex(...)}` `` /
  `"${root_or_parent_with_any_config}"` (parsed via three small regexes) → walk up from
  `filepath.Dir(target)` to `repoRoot` inclusive, using `os.Stat` (filename form),
  `os.ReadDir` + `regexp.MatchString` (regex form), or `os.Stat` over each of `directConfigs`
  (any-config form); first matching directory wins, else `(repoRoot, true)` (the "root" fallback
  the syntax itself names).
- Anything else → `("", false)` — unsupported, caller emits `Skipped`.

### `sandbox.go`

```go
// stageSandbox copies files (copy_targets: exactly targets; expanded: every regular file directly
// inside dir) from dir into a fresh temp directory, returning the temp dir and a cleanup func.
// Every copied file's path relative to dir is preserved, so a Finding's path can always be
// remapped back through dir to repoRoot -- see remapFindings.
func stageSandbox(sandboxType, dir string, targets []string) (sandboxDir string, cleanup func(), err error)
```

- `copy_targets`: copies exactly the batch's `targets` (already resolved-dir-relative), creating
  parent directories as needed.
- `expanded`: `os.ReadDir(dir)` non-recursively, copies every regular file found (this naturally
  includes the matched targets, since they live in `dir`).
- `cleanup` is `func() { os.RemoveAll(sandboxDir) }`, always deferred by the caller immediately
  after staging succeeds.

```go
// remapFindings rewrites every finding's File from a path relative to base (the resolved RunFrom
// directory a command actually ran against -- real or, when sandboxed, mirrored) back to a path
// relative to repoRoot, the report's established contract. A no-op whenever base == repoRoot
// (every command that doesn't use RunFrom/SandboxType today), so it is safe to call
// unconditionally for every job.
func remapFindings(findings []Finding, base, repoRoot string)
```

An absolute `Finding.File` (should not happen with today's parsers, but guarded) is remapped
directly against `repoRoot`, skipping the `base` join.

### `run.go` changes

**`buildJobs`**: after the existing unsupported-var/output-format/parser checks (unchanged, still
command-level), the current blanket `RunFrom != "" → Skip` / `SandboxType != "" → Skip` checks are
replaced by:

1. For each matched file, call `resolveRunFrom`. If any file's `RunFrom` value is unsupported
   (`ok == false`), emit one `Skipped` event for the whole command (matching today's per-command
   granularity) and move to the next command.
2. Group files by resolved directory (a `map[string][]string`, iterated in sorted-directory order
   for determinism, matching the existing sorted-file-within-linter convention).
3. If `cmd.SandboxType` is set and isn't `copy_targets`/`expanded`, emit one `Skipped` event for the
   whole command (same granularity) and move on.
4. For each `(resolvedDir, files)` group: build one job if `cmd.Batch`, else one job per file —
   exactly today's batching logic, just now per-group instead of once globally. Each `job` gains a
   `resolvedDir string` field (the group's directory) alongside the existing fields.

Groups where `resolvedDir == repoRoot` and `SandboxType == ""` behave byte-for-byte as today (the
`${parent}`/empty-`RunFrom` common case never splits, since every file resolves to the same
directory) — this plan changes zero observable behavior for the ~172 already-working commands.

**`runBatch`** (per job): before invoking, if `job.cmd.SandboxType != ""`, calls `stageSandbox`
using `job.resolvedDir` and `job.batch` (deferring `cleanup()`); the invocation's working directory
becomes the sandbox dir instead of `job.resolvedDir`, and `${target}` substitutes the same relative
paths (they're identical in both dirs, by construction). Otherwise, working directory is
`job.resolvedDir` directly (repoRoot today, unchanged). After parsing, `remapFindings(findings,
job.resolvedDir, repoRoot)` runs unconditionally before `ApplyIssueURL` — a no-op for every
resolvedDir == repoRoot job.

`runOneInvocation`'s `repoRoot string` parameter (currently doubling as "the command's Dir") is
renamed/repurposed to accept the resolved working directory directly; its caller passes
`job.resolvedDir` or the sandbox dir as appropriate.

## Testing approach

- `runfrom_test.go`: one test per resolution form, using real temp-dir fixtures (marker files at
  various depths) — `${parent}`/empty (→ repoRoot), `${target_directory}`, `root_or_parent_with`
  (found at an intermediate level, found at repoRoot itself, not found at all → repoRoot fallback),
  `root_or_parent_with_regex`, `root_or_parent_with_any_config` (multiple `DirectConfigs`, first
  one found wins), and an unrecognized literal (`ok == false`).
- `sandbox_test.go`: `copy_targets` copies exactly the given targets (sibling files in the same
  real directory must NOT appear in the sandbox); `expanded` copies every top-level file in the
  directory (a file in a subdirectory must NOT appear); cleanup actually removes the temp
  directory. Every assertion reads the real filesystem, no mocking.
- `run_test.go`: extends `fakeToolSrc` with a case that prints its own `os.Getwd()` and
  `os.ReadDir(".")` listing, and new fake linters covering: `${target_directory}` alone,
  `copy_targets` alone, `expanded` alone, the `${parent}`+`copy_targets` combo (mirroring `snyk`),
  and a `Batch: true` command whose matched files span two different resolved directories
  (asserting two separate `Running`/invocation events, not one). Each asserts the exact `Finding`
  values after remapping, proving paths land back at repoRoot-relative, not sandbox- or
  resolvedDir-relative.

## Global constraints (carried into every task)

- No new `go.mod` dependencies — directory walks and file copies are plain `os`/`path/filepath`.
- Every test asserts exact values (files present/absent, exact `Finding` contents, exact resolved
  directories), never just "no error."
- `remapFindings` must be a no-op whenever `base == repoRoot` — existing tests for the ~172
  already-working commands must keep passing unmodified.
- Commits signed (`-S`), commitlint conventions per `.agents/skills/git-commit/SKILL.md`.
- `go build ./... && go vet ./... && go test ./... -count=1 -race` clean before every task is done
  (the `-race` flag matters here: sandbox staging + concurrent workers from v0.3.1 touch the
  filesystem per job, and each job's temp dir must be genuinely private to that job).
- Do not modify `match.go`, `parse.go`, or the output-format dispatch switch in `run.go` — this
  plan's entire surface is the two new files plus `buildJobs`/`runBatch`/`runOneInvocation` in
  `run.go`.
