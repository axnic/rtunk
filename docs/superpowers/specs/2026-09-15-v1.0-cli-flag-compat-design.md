# v1.0 — CLI Flag Compatibility: Design

**Status:** self-ruled (user granted full autonomy: "Go pour la V1, je validerais ou non le
comportement" — proceed, behavior gets validated afterward. Ground every decision in the real
`trunk` CLI's actual `--help` output, v1.25.0, installed on this machine).

## Goal

ROADMAP.md's v1.0 milestone: "Be compatible with most of trunk's CLI flags across the commands
implemented in the milestones above, so that scripts, CI pipelines, and muscle memory built around
`trunk` carry over to `rtunk` with minimal changes."

This is the last milestone before v1.0 proper and is explicitly a breadth pass over flags of
functionality that already exists — not a vehicle for new engine features. Every decision below
either (a) maps a trunk flag onto behavior rtunk already has, under trunk's own flag name, or (b)
rules a trunk flag out because the underlying capability doesn't exist and is out of this pass's
scope.

## Method

Real trunk's flags were captured directly from the installed binary (`trunk --help`, `trunk check
-h`, `trunk fmt -h`, `trunk init -h`, `trunk deinit -h`, `trunk upgrade -h`, `trunk actions -h`,
`trunk actions history -h`, `trunk git-hooks -h`, `trunk config/cache/tools/plugins -h`), then
compared field-by-field against rtunk's current `internal/cli/*.go` command structs. Every flag
trunk exposes falls into one of three buckets:

1. **Already equivalent** — rtunk has the same behavior under a different name/shape. Add the
   trunk name as an alias (via Kong's `aliases:"..."` tag, confirmed supported in the vendored
   `github.com/alecthomas/kong v1.16.1`) rather than renaming rtunk's own field, so no existing
   flag breaks.
2. **Real gap, cheaply closable** — trunk behavior rtunk doesn't have yet, but is a small,
   self-contained addition consistent with rtunk's existing architecture (e.g. `--filter`).
   Implement it.
3. **Out of scope** — trunk behavior backed by a subsystem rtunk deliberately doesn't have
   (daemon, changed-file/git-index detection, lint-result caching, diff rendering, cloud
   upload, interactive prompts, ignore-file support). Documented as a non-goal, not implemented.

Bucket 3 is not scope creep avoidance for its own sake: every one of these has already been ruled
out at least once earlier in this project (AGENTS.md's permanent daemon/telemetry/cloud-account
ban; v0.6/v0.7's "no interactive prompts anywhere in rtunk" precedent). This pass is consistent
with, not a departure from, that history.

## Decisions, per command

### Global flags (`internal/cli/cli.go`)

| trunk flag                                     | Decision                                                   | Why                                                                                                                                                                                                                                                |
| ---------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--ci`                                         | **Add**, global no-op bool                                 | rtunk is already always CI-safe (no daemon, no prompts, deterministic output) — accepting a flag scripts pass defensively costs nothing and directly serves "scripts...carry over with minimal changes."                                           |
| `-v, --verbose`                                | **Add**, global no-op bool                                 | rtunk already unconditionally streams per-file `running`/`done` progress to stderr (`printEvent`). There is no quieter default to make louder. Accepting it doesn't misrepresent capability — the behavior it asks for is already happening.       |
| `--print-failures`                             | **Add**, global no-op bool, `check`/`fmt` only (see below) | rtunk already always prints `Failed` events unconditionally. Same reasoning as `-v`.                                                                                                                                                               |
| `--monitor`                                    | Not added                                                  | Enables trunk's daemon. Permanently out of scope per AGENTS.md — silently accepting and ignoring a flag that asks for a background daemon would misrepresent what rtunk just did, unlike `--ci`/`-v` where the requested behavior is already true. |
| `--no-progress`, `--ci-progress`               | Not added                                                  | No progress-bar/spinner UI exists to suppress or rate-limit.                                                                                                                                                                                       |
| `--action_timeout`                             | Not added                                                  | No timeout enforcement exists; adding the flag without enforcing it would be a lie, and adding real enforcement is a new feature outside this pass.                                                                                                |
| `--color`                                      | Not added                                                  | rtunk never emits ANSI color; nothing to toggle.                                                                                                                                                                                                   |
| `--token`, `--upload`, `--series`, `--replace` | Not added                                                  | Cloud/dashboard upload — permanently out of scope per AGENTS.md.                                                                                                                                                                                   |

`--print-failures` is declared on `checkRunCmd`/`fmtCmd` specifically (not root `CLI`) since it is
check/fmt-specific in real trunk too (its own help lists it under check's own flag block, not the
bare top-level `trunk --help`).

### `check` / `fmt` (`internal/cli/check.go`, `internal/cli/fmt.go`)

| ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--filter <list>`                                                                                 | **Add**                                                                                                                                                                                                                                                                                                                                                               | Comma-separated linter ids; a `-` prefix on an id excludes it, otherwise the list is an allow-list (matches trunk's own stated semantics exactly: "comma separated list of linters... to include or exclude"). Issue-code-level filtering (trunk's `-eslint/SC2301` form) is **not** included: rtunk's `output.Finding` filtering at that granularity is a separate, deeper feature; linter-id granularity covers the common case ("run only these linters" / "skip that one"). |
| `--exclude <list>`                                                                                | **Add**                                                                                                                                                                                                                                                                                                                                                               | Trunk's own definition: "shorthand for an inverse --filter". | `--sample`, `--upstream`, `--index`, `--index-file`, `--commit-ref`, `--commit-ref-from-pre-push` | Not added                                                                                                                                                                                                                                                                                                                                                             | All depend on git-changed-file/git-index detection, a real subsystem rtunk doesn't have. ### `check enable`/`disable`/`list`, `actions list`/`enable`/`disable`

No changes. Real trunk's own `-h` output for each of these leaves is just the global noise set
(`--version`, `--monitor`, `--ci`, ...) with no command-specific flags beyond the ID/linter
argument list rtunk's `checkEnableCmd`/`checkDisableCmd`/`actionsEnableCmd`/`actionsDisableCmd`
already have.

### `actions run` (`internal/cli/actions.go`)

Real trunk's own `--help` lists `run` as _both_ a subcommand of `actions` and a top-level
shortcut (`trunk run <action-id>`, visible in `trunk --help`'s own subcommand list). **Add**
`rtunk run` as a top-level alias of `rtunk actions run` (same `actionsRunCmd` struct, registered
a second time on `CLI` under the name `run`) — a direct, cheap compat win for the exact form trunk
scripts use.

### `actions history` (`internal/cli/actions.go`)

Trunk's flag is named `--count`; rtunk's existing field is `Limit int` (`default:"20"`, same
concept). **Add** `aliases:"count"` to the existing `Limit` field — no rename, no behavior change.

### `git-hooks` (`internal/cli/githooks.go`)

Trunk's subcommand is `git-hooks sync` ("sync git hooks with trunk.yaml") where rtunk's is
`git-hooks install`. For rtunk's simpler model (install is already idempotent — re-running it
just rewrites the same hook files) these are the same operation. **Add** `sync` as a Kong command
alias (`aliases:"sync"`) on the existing `Install` field — no new Run logic.

Trunk's `git-hooks callback` (the internal entrypoint the installed hook shim itself invokes) has
no rtunk equivalent to be compatible with: rtunk's installed hook shim already execs `rtunk
actions run --hook <name>` directly (v0.5), there is no separate callback command. Not added — N/A,
not a gap.

### `init` (`internal/cli/init.go`)

No changes. Every other trunk `init` flag (`--lock`, `-y/-n`, `--single-player-mode`,
`--only-detected-*`, `--allow-existing`) was already explicitly ruled a non-goal in v0.7's own
design doc (interactive prompts, checksum locking, gitignored config, detection wizard are all
out of scope for reasons that still hold). `--force` already exists under the same name and
meaning as trunk's own `--force`. Nothing left to reconcile.

### `deinit` (`internal/cli/init.go`)

Trunk's `-y, --yes` skips a confirmation prompt. rtunk's `deinit` never prompts (v0.7's own
established non-goal). **Add** `-y, --yes` as a documented no-op bool — scripts that defensively
pass it (the common case for any automated deinit) don't fail; it asks for behavior rtunk already
has.

### `upgrade` (`internal/cli/upgrade.go`)

Trunk's `--dry-run` is exactly rtunk's existing `Check` field ("report whether a newer release is
available, without installing it"). **Add** `aliases:"dry-run"` — no rename. Trunk's `scope`
positional (`check|plugins|runtimes|tools|cli`) selects which of several upgrade domains to touch;
rtunk's `upgrade` only ever has one domain (itself, trunk's own `cli` scope). Not added: there is
only one thing to scope, and rtunk already does exactly that unconditionally — an argument with a
single legal value that does nothing when supplied is complexity with no payoff. `-y/-n`
(prompts), `--filter`, `--apply-to` (linter-upgrade-specific) are not added — no prompts, no
linter-upgrade concept exists here.

### `config print`, `download`, `where`, `exec`, `cache`

No changes. `config print` already supports `--output yaml|json` and `--all`; real trunk's own
`config`/`cache` extended-subcommand help exposed no further leaf flags to reconcile against
(confirmed via direct probing — both fall through to generic global flags only). `download` /
`where` / `exec` have no trunk equivalent at all (trunk's closest analogs, `install` / `tools
install|enable|disable|list`, are bulk, config-driven operations with a fundamentally different
shape from rtunk's single-item-by-id design, already a deliberate v0.2 divergence) — there is no
trunk flag surface to be compatible with on commands that don't correspond 1:1.

## Implementation shape

All additions are struct-tag-only (`aliases:"..."`, `short:"..."`) or small, local additions:

- One new shared helper, `filterLinters(cfg config.Config, filter, exclude string)
(config.Config, error)` (new file `internal/cli/filter.go`, used by both `check.go` and
  `fmt.go`): parses the comma list (bare id = allow, `-id` = deny), validates every named id
  exists in `cfg.Lint.Definitions` (unknown id in `--filter`/`--exclude` is a user error, reported
  clearly — matching this codebase's existing `editEnabled`-family validation precedent, not
  silently ignored), and returns a copy of `cfg` with `Lint.Definitions` trimmed accordingly.
  `--filter` and `--exclude` are mutually exclusive (real trunk's own docs describe `--exclude` as
  sugar for one specific `--filter` shape, not a separate independent mechanism) — passing both is
  a usage error.
- Three new no-op bool fields (`CI`, `Verbose` on `CLI`; `PrintFailures` on `checkRunCmd`/
  `fmtCmd`), each with a one-line doc comment explaining it's accepted-for-compatibility.
- `aliases`/`short` tag additions on five existing fields (`checkRunCmd.Fix`, `fmtCmd.Check`,
  `actionsHistoryCmd.Limit`, `gitHooksInstallCmd`'s command registration, `upgradeCmd.Check`) plus
  one new no-op field each on `checkRunCmd` (`NoFix`) and `deinitCmd` (`Yes`).
  - **`gitHooksInstallCmd`'s alias needs a Kong-mechanics check the implementer must resolve**:
    `aliases` on a `cmd:""` field tag aliases the _command name_ ("install" also answering to
    "sync"), which is exactly the desired `git-hooks sync` ≡ `git-hooks install` outcome — the
    struct tag goes on `gitHooksCmd.Install gitHooksInstallCmd \`cmd:"" aliases:"sync" ...\``, not
inside `gitHooksInstallCmd` itself.
- One new top-level command registration in `cli.go`: `RunCmd actionsRunCmd` (reusing the existing
  struct — both `CLI.ActionsCmd.Run` and `CLI.RunCmd` are the same `actionsRunCmd` type, Kong runs
  whichever path was invoked).

No changes to `pkg/trunk/engine`, `pkg/trunk/config`, `pkg/trunk/actions`, `pkg/trunk/githooks`,
or `pkg/trunk/upgrade` — every addition lives in `internal/cli`, confirming this milestone really
is the "breadth pass over existing functionality" ROADMAP.md describes it as, not new capability.

## Testing strategy

- `filterLinters`: table tests — allow-list (only named ids' definitions survive), deny-list
  (`-id` removes just that one), mixed list is a usage error, unknown id is a usage error, both
  `--filter` and `--exclude` given is a usage error, neither given returns `cfg` unchanged.
- `check --filter`/`--exclude`/`fmt --filter`/`--exclude`: end-to-end against a real small
  multi-linter fixture repo (reusing this codebase's existing check/fmt integration-test fixture
  pattern) — assert only the surviving linter(s) actually ran (via `engine.Event`/stdout report),
  not just that the flag parsed.
- `-y`/`-n`/`--no-fix`/`--ci`/`-v`/`--print-failures`/`deinit -y`: flag-parses-and-is-accepted
  tests (Kong parse succeeds, exit code / behavior identical to the flag being absent) — these are
  no-ops, so the assertion is "accepted, no behavior change," not a functional assertion.
- `actions history --count`: same test as the existing `--limit` test, invoked with `--count`
  instead, asserting identical output.
- `git-hooks sync`: same test as the existing `git-hooks install` test, invoked as `git-hooks
sync`, asserting identical resulting hook files.
- `rtunk run <id>` / `rtunk actions run <id>`: same underlying test run through both invocation
  paths, asserting identical behavior.
- `upgrade --dry-run`: same test as the existing `--check` test, invoked with `--dry-run`.

## Non-goals (ruled, disclosed)

- Issue-code-level `--filter`/`--exclude` (trunk's `-eslint/SC2301` form) — linter-id granularity
  only.
- `--ignore`/`--force` (no ignore-file/glob mechanism exists — a real engine feature, not a flag
  shim).
- `-a/--all`, `--sample`, `--upstream`, `--index`, `--index-file`, `--commit-ref*` — all depend on
  changed-file/git-index detection, a subsystem rtunk doesn't have.
- `--cache` (no lint-result cache), `--diff` (no synthesized diff view), `--scope
{all|security}` (no security-linter-subset concept).
- `--monitor`/daemon, `--token`/`--upload`/`--series`/`--replace` (cloud upload), `--action_timeout`
  (no enforcement) — permanently out of scope per AGENTS.md or would require enforcement that
  doesn't exist and isn't being added here.
- `--no-progress`/`--ci-progress`/`--color` — no progress UI or color output exists to control.
- `upgrade`'s `scope` positional, `-y/-n` prompts anywhere, `--lock`/`--single-player-mode`/
  `--only-detected-*` on `init` — all already-established non-goals (single-scope upgrade,
  zero-interactive-prompt precedent, v0.7's own init non-goals).
- `trunk git-hooks callback` — no rtunk equivalent needed; rtunk's hook shim has no separate
  callback entrypoint to be compatible with.
