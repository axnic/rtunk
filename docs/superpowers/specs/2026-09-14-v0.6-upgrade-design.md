# v0.6 — Self-Upgrade: Design

**Status:** self-ruled (user granted full autonomy for v0.6+v0.7 via SDD; ground decisions in real
`trunk`'s behavior where relevant, self-rule where rtunk's own scope is deliberately narrower).

## Goal

Implement ROADMAP.md's v0.6 milestone: `rtunk upgrade` — check for and install a newer release of
**rtunk itself** (never linters/tools/runtimes/plugins, which are already reproducibly pinned via
`trunk.yaml`'s own `enabled:` lists per AGENTS.md's reproducibility rule), fetched from rtunk's own
GitHub Releases, and only ever triggered manually.

## Ground truth from the real `trunk upgrade` (v1.25.0, installed on this machine)

`trunk upgrade` is **much broader** than rtunk's own v0.6: it has five scopes (`check | plugins |
runtimes | tools | cli`), interactive `-y`/`-n` prompts, `--apply-to`/`--filter`, a `--dry-run`,
etc. — because real trunk treats "upgrade" as "bump every pinned version in trunk.yaml to latest,"
not just "update the trunk binary." **rtunk's v0.6 is deliberately narrower** — ROADMAP.md's own
wording ("check for and install a newer release of rtunk itself") and AGENTS.md's reproducibility
rule (no silent version drift for linters/tools) rule out copying that breadth. Ground truth here
is "don't copy trunk's scope," not "copy trunk's behavior" — the one part worth mirroring is naming
the flag that skips writing anything `--check` (rtunk's own existing convention: `fmt --check`,
consistent with itself over matching trunk's own `--dry-run` name for the same idea).

## A real prerequisite gap, found while researching this feature

`cmd/rtunk/main.go` embeds **no version at all** today — no ldflags `-X`, no `--version` flag
anywhere in the CLI. `rtunk upgrade` cannot know whether an upgrade is needed without knowing its
own current version, so this feature necessarily adds version embedding as a prerequisite, not
scope creep.

A second, more consequential gap: **this repo has no CI or release pipeline** (no
`.github/workflows/`, no goreleaser config) — nothing today would ever publish a GitHub Release for
`rtunk upgrade` to find. Setting one up is a real, useful next step, but it is **out of scope for
this feature** and explicitly not done here: publishing infrastructure that could auto-publish
signed releases under the user's own GitHub identity is a side effect on a shared system outside
this worktree, exactly the class of action the standing instructions say to check about first
rather than self-rule overnight. `rtunk upgrade` is built and tested (against a stubbed GitHub API,
this codebase's own established no-live-network-in-tests convention) to work correctly the moment
real releases exist in the asset-naming shape this spec defines below — but until the user sets up
that publishing pipeline (or asks for it explicitly), running `rtunk upgrade` against the real
`xunleii/rtunk` repo will correctly report "already up to date" or a 404, never crash.

## Design

### Version embedding

`cmd/rtunk/main.go` gains a package-level `var version = "dev"`, settable at build time via
`-ldflags "-X main.version=vX.Y.Z"` (the standard, dependency-free Go convention — no new library).
Passed into `internal/cli` via a new exported `cli.Version` var, set by `main()` before calling
`cli.Run` (mirrors how `cli.Run`'s own signature already takes explicit stdout/stderr rather than
reaching for a package-global — `Version` is the one genuine exception, since Kong's own
`kong.VersionFlag` mechanism for `--version` needs a `kong.Vars{"version": ...}` string available
at `kong.New(...)` construction time inside `Run`, not passable as a `Run()` parameter without
changing every existing call site). A root-level `--version` flag (via `kong.VersionFlag`,
printing `cli.Version` and exiting 0) is added alongside — a natural, essentially-free companion
once embedding exists, and standard CLI-user expectation (real trunk has one too).

When built via `go build` directly (no ldflags, e.g. local dev or `go install .../rtunk@latest`),
`version` falls back through: the ldflags value if set (non-`"dev"`) → `debug.ReadBuildInfo()`'s
own `Main.Version` (populated automatically for a `go install <module>@<version>` install, a real
and common install path for a Go CLI) → the literal `"dev"`. `rtunk upgrade` against a `"dev"`
build always reports "cannot determine current version, skipping" (exit 0, not an error) rather
than guessing.

### `pkg/trunk/upgrade` (new package)

```go
// Release is the subset of GitHub's release API response this package needs.
type Release struct {
	TagName string  `json:"tag_name"`
	Assets  []Asset `json:"assets"`
}

type Asset struct {
	Name               string `json:"name"`
	BrowserDownloadURL string `json:"browser_download_url"`
}

// LatestRelease fetches owner/repo's latest GitHub release (unauthenticated -- matches
// AGENTS.md's own listed exception for this exact call). apiBase defaults to
// "https://api.github.com" when "" (test seam, same purpose as pkg/trunk/download's own
// httptest-server-backed tests -- never a live network call in a test).
func LatestRelease(apiBase, owner, repo string) (Release, error)

// AssetName is the release-asset filename this platform's rtunk binary is published as:
// "rtunk_<goos>_<goarch>" (bare binary, no archive/extension -- rtunk is already "a single
// static binary" per AGENTS.md, and skipping tar/zip extraction keeps self-upgrade's own code
// path simpler than a general-purpose download recipe needs to be). Real value e.g.
// "rtunk_darwin_arm64".
func AssetName(goos, goarch string) string

// Available compares the release's own TagName (leading "v" trimmed) against currentVersion by
// plain string inequality -- GitHub's own "latest release" endpoint already returns the most
// recently published non-prerelease release, so rtunk doesn't need its own semver ordering logic
// to trust "different from what's running" as "an upgrade." currentVersion == "dev" always
// reports false (see main.go's own fallback chain above).
func Available(rel Release, currentVersion string) (newVersion string, available bool)

// Apply downloads assetURL (reusing pkg/trunk/download.FetchBlob's existing content-addressed
// blob cache -- no new HTTP-download code path) and atomically replaces targetPath (typically
// os.Executable()'s own result) with it, chmod +x. Same temp-file-then-os.Rename-on-the-same-
// filesystem idiom already used throughout this codebase (see e.g. download's own
// finalizeInstall) -- os.Rename over a currently-running executable's own path is the standard,
// well-established Unix self-update pattern (the OS keeps the old inode open for the still-
// running process; only a future invocation sees the new file). Windows is unsupported (returns
// an explicit error) -- this project has already ruled out full Windows shim support elsewhere
// (v0.2), and Windows cannot rename over a running executable's own path at all.
func Apply(cacheDir, assetURL, targetPath string) error
```

### CLI (`internal/cli/upgrade.go`)

```go
type upgradeCmd struct {
	Check bool `help:"Report whether a newer release is available, without installing it."`
}
```

`Run`: resolve current version from `cli.Version` (falls back per main.go's own chain if `cli.Run`
itself was invoked with `Version` unset — defensive, but `main.go` always sets it in practice).
Call `upgrade.LatestRelease("", "xunleii", "rtunk")`; if `currentVersion == "dev"`, print "cannot
determine current version, skipping" and return nil. Otherwise `upgrade.Available(rel,
currentVersion)`:

- Not available: print "rtunk is up to date (<version>)", return nil.
- Available, `--check`: print "a newer release is available: <current> -> <new>", return a plain
  error (non-zero exit) — mirrors `fmt --check`'s own established convention (a check flag that
  fails non-zero when the checked-for condition needs action, so CI can gate on it).
- Available, no `--check`: resolve the matching asset via `upgrade.AssetName(runtime.GOOS,
runtime.GOARCH)`, error clearly if the release has no such asset (e.g. this repo genuinely has
  no releases yet, or a platform this project doesn't publish for) rather than a confusing 404;
  otherwise `os.Executable()` for the target path, `upgrade.Apply(...)`, print "upgraded <current>
  -> <new>".

### Testing strategy

- `pkg/trunk/upgrade`: `LatestRelease`/`Available`/`AssetName` against an `httptest.Server`
  returning a real-shaped GitHub releases JSON body (exact tag/asset names asserted, matching this
  codebase's "exact values, never just no error" standard); `Apply` against a real local HTTP
  server serving a small fixture binary, asserting the target path's exact new content and that
  its executable bit is set, and a **live self-replace regression test**: build a tiny real Go
  binary fixture that prints a distinguishable string, use it as `targetPath`, run `Apply`, then
  actually `exec.Command(targetPath).Output()` and assert the NEW content runs — proving the
  rename-over-a-path pattern genuinely works, not just that bytes landed on disk.
- `internal/cli`: `upgradeCmd`'s three outcomes (up to date / check-mode-available-exits-nonzero /
  applies-and-reports), driven against a stubbed `apiBase` (the CLI needs `LatestRelease`'s
  `apiBase` param threaded through, or a package-level override var for tests only — decide the
  exact seam in the plan; never a live call to `api.github.com` in a test).

## Non-goals (ruled, disclosed)

- No CI/release-publishing pipeline (goreleaser, GitHub Actions) is set up as part of this feature
  — see "A real prerequisite gap" above. `rtunk upgrade` is built and tested to work the moment one
  exists, in the exact asset-naming shape (`rtunk_<goos>_<goarch>`) this spec defines.
- No checksum/signature verification — already an explicit prior project decision (`git log`:
  "Postpone --secure/signature verification to v1+"), not reopened here.
- No semver range/pre-release/channel logic — trusts GitHub's own "latest release" designation as
  the single source of truth for "what's newest," matching this feature's own narrow scope (one
  binary, one channel).
- No Windows self-replace support (`Apply` returns an explicit error on `GOOS == "windows"`) —
  consistent with this project's existing, already-ruled Windows-shim non-goal.
- No interactive confirmation prompt (`-y`/`-n`) — rtunk has no interactive-prompt precedent
  anywhere else in its CLI (fully scriptable/CI-oriented throughout); `rtunk upgrade` just upgrades
  when a newer release exists, same non-interactive philosophy as every other command.
