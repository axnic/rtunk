# v0.9.1 Event Stream and Plain Renderer: Design

**Status:** design agreed with the user in conversation (2026-09-26) before this spec was written.
This is sub-project 1 of 4 of ROADMAP `v0.9`; see Scope.

## Scope

ROADMAP `v0.9` ("Output and UX", [ROADMAP.md](../../../ROADMAP.md), [docs/ux.md](../../ux.md)) is
decomposed into four sub-projects, each with its own spec and plan:

1. **Event stream + plain renderer** (this spec).
2. `--format human|sarif|json` on `check` and `fmt`. Follows this spec directly.
3. TTY live view.
4. Filtered `linters list` / `actions list`.

This spec covers only #1. It builds the renderer seam and the first renderer (plain, non-TTY) that
#2 and #3 plug into.

## Goal

`check` and `fmt` stop printing ad hoc and drive a `Renderer` fed by the engine's event stream. The
plain renderer produces the non-TTY output specified in docs/ux.md ("Non-TTY fallback", "Issues
output"): one stderr line per finished linter, then a stdout report listing every issue, a
`FAILURES` section carrying the run-log uid, and a summary footer. Renderers hold no business logic.
Exit codes are unchanged.

## Current state

- `engine.Run` (`pkg/trunk/engine/engine.go`) already streams `Event` values (`Running`, `Done`,
  `Skipped`, `Failed`), one `Running` per command invocation and exactly one terminal event per
  linter (a linter with a `Skipped` command can emit several `Skipped`, one per command).
- `internal/cli/check.go` and `internal/cli/fmt.go` consume it ad hoc:
  - stderr: `printEvent` (check) and `printFmtEvent` (fmt, `--fix` pass, `--verify-stable`) print
    `running|done|skipped|failed` lines, including every `Running` event.
  - stdout: `printReport` (`file:line[:col] severity [rule] message`, then `N issue(s) in M
file(s)`), `printFmtReport` and `printFmtCheckReport` (one file per line, then `N file(s)
reformatted|would be reformatted`), all with a `(N linter(s) skipped: ...)` parenthetical.
  - aggregation: `drainRunEvents` (`check.go`) and `collectChangedByLinter`
    (`internal/cli/fmt_stability.go`) accumulate findings, changed files, skipped linters and the
    first failure while printing.
  - `formatFinding` renders one issue line.
- `check --fix` runs a formatter pass (`runFormatOnce` / `runStableFormat`, `fmt_stability.go`)
  printed via `printFmtReport`, then the checking pass printed via `printReport`.
- Missing from the stream, needed by docs/ux.md:
  - number of files checked (only findings carry a file; clean files are invisible);
  - run duration (not measured anywhere in the CLI; `runlog.Writer` keeps a private start time);
  - the run-log uid for failures (`runlog.Writer` exposes no name; `rtunk logs list` derives it
    from the file name);
  - high/medium/low severity: `output.Finding.Severity` is `error|warning|info`
    (`pkg/trunk/output/finding.go`).
- `--no-progress` (which docs/ux.md says honors and which trunk also has) does not exist.

## Design

### 1. Package `internal/cli/render`

```go
type Renderer interface {
    Event(engine.Event)      // called for every event, in arrival order, from one goroutine
    Close(Summary) error     // writes the stdout report; called once, after the stream is drained
}

type Summary struct {
    Elapsed time.Duration // measured by the CLI around the engine run(s)
    RunLog  string        // runlog Writer.Name(); "" when logging is disabled
    Skipped []string      // "linter [note]", deduped by linter, as drainRunEvents builds it today
    Changed []string      // fmt only: repoRoot-relative files reformatted, or that would be (--check)
}
```

- Renderers hold no business logic: they format what `Event` and `Summary` carry. Aggregation of
  findings, failures and file counts inside the renderer is presentation state only (grouping and
  counting), not decisions.
- `check`, `fmt` and `check --fix`'s formatter pass construct a renderer and call `Event` for each
  event; the loop that reads the channel stays in `internal/cli` (it replaces `drainRunEvents` and
  `collectChangedByLinter`'s printing, and keeps returning what the exit-code logic and
  `--verify-stable`'s per-linter attribution need: findings count, `changed`, `skipped`, first
  `failed` error).
- One implementation now: `plain`. `Renderer` is the seam for #2 (`human`, `sarif`, `json`) and #3
  (live view). Constructor: `render.NewPlain(stdout, stderr io.Writer, opts Options)` with
  `Options{Command Kind (Check|Fmt|FmtCheck), NoProgress bool, NoColor bool}`.
- `NoColor` is set from `NO_COLOR` (set and non-empty, per no-color.org). Plain emits no color, so
  there is nothing to strip yet; the switch is read and stored so #2 inherits it.

### 2. Plain output

**stderr, progress (streamed).** One line per terminal event, in arrival order; `Running` events
are dropped:

```text
✔ markdownlint   done      7 issues
✔ gofmt          done      clean
▲ shfmt          skipped   unsupported output format "x"
✖ gitleaks       failed    <first line of err>
```

Exact wording and alignment are tuned in tests (see Open questions). `--no-progress` (new flag on
`check` and `fmt`) suppresses every stderr progress line. It does not suppress warnings or errors
that are not progress (`rtunk: no files to check`, partially staged warnings, the log warning,
`warnIfRecentOverlap`, errors printed by `cmd/rtunk/main.go`).

**stdout, report (`Close`).** Modeled on docs/ux.md "Issues output":

```text
ISSUES   27 in 12 files

.agents/skills/git-commit/SKILL.md                                 (9)
  22:0   low   Fenced code blocks should have a language specified   markdownlint/MD040
  32:0   low   Fenced code blocks should have a language specified   markdownlint/MD040

pkg/trunk/download/shim.go                                         (2)
  57:3   high  QF1012: Use fmt.Fprintf(...) instead of ...           golangci-lint2/staticcheck

FAILURES
  ✖ gitleaks   failed to run   rtunk logs show 3f9a2c

Checked 232 files with 6 linters in 14.2s
✖ 27 issues (5 high · 4 medium · 18 low) · 1 failure
```

Rules:

- `ISSUES   N in M files` header only when N > 0. Then one block per file, files sorted
  alphabetically by path: header line `<path>  (<count>)` (count = issues in that file), then EVERY
  issue of the file sorted by line, then column. No folding of repeated issues, no per-rule
  summary.
- Issue line: `line:col  severity  message  linter/rule`. `line:col` from `Finding.Line`/`Column`
  (0 stays `0`, matching the mockup's `22:0`); `linter/rule` is `Finding.Linter` + `/` +
  `Finding.RuleID`, or `Finding.Linter` alone when `RuleID` is empty. `Finding.URL` is not printed
  (the old `formatFinding` appended it; it returns with `--format json|sarif` in #2).
- Severity words `high`, `medium`, `low` are always printed. Glyphs `✖` (high), `▲` (medium), `·`
  (low) accompany them in the summary footer; in issue lines the word alone is printed and the
  glyph is reserved for the human renderer (color plus glyph, #2/#3). Plain emits no ANSI escapes
  and no color.
- Severity mapping lives in the renderer: `error` -> high, `warning` -> medium, `info` -> low; an
  unknown value maps to low. `output.Finding` is not changed.
- `FAILURES` section only when at least one linter failed: one line per `Failed` event,
  `✖ <linter>  failed to run  rtunk logs show <uid>`, in the order of first failure per linter
  sorted alphabetically. `<uid>` is `Summary.RunLog`; the trailing `rtunk logs show <uid>` is
  omitted when it is empty (log disabled). A `Failed` event with no linter-level cause beyond the
  error keeps the error text on the stderr progress line, not in `FAILURES`.
- Footer, always printed:
  `Checked N files with M linters in Ts`, then the verdict line
  `✖ N issues (a high · b medium · c low) · F failure(s)`. N is the count of unique files across
  the `Files` of every terminal event; M is the count of distinct linters that emitted a terminal
  event (`Skipped` included); T is `Summary.Elapsed` with one decimal. A clean run prints
  `Checked N files with M linters in Ts` and a clean verdict line (`✔ no issues`), with `· F
failure(s)` appended only when F > 0. Singular forms (`1 issue`, `1 failure`) are used.
- Skipped linters: when `Summary.Skipped` is non-empty a line
  `Skipped  N linter(s): a [note], b [note]` precedes the footer, replacing today's parenthetical.
- No files: the existing `rtunk: no files to check|format` early return in `check.go`/`fmt.go` is
  unchanged (stderr, exit 0, no report).

**`fmt` report.** Same family, same footer style:

```text
REFORMATTED   3 files

  docs/ux.md
  pkg/trunk/engine/engine.go
  README.md

Checked 232 files with 4 linters in 6.1s
✔ 3 files reformatted
```

- `fmt` lists `Summary.Changed`, sorted, under `REFORMATTED   N files`; `fmt --check` uses
  `WOULD REFORMAT   N files` and the verdict `✖ N files would be reformatted`; nothing changed
  prints `✔ no files reformatted` (`✔ no files would be reformatted` with `--check`). The
  `FAILURES` section, skipped line and `Checked ... in Ts` line are identical to `check`.
- `--verify-stable`: the report is emitted once, after both rounds, from the merged `changed`
  (`dedupeSortedFiles`) as today; per-round event lines still stream to stderr. The
  `unstableFormatError` verdict is still returned as the command error, unchanged
  (`fmt_stability.go`).
- `check --fix`: the formatter pass gets its own `fmt` renderer instance and report (stdout, as
  `printFmtReport` today), then the checking pass gets a `check` renderer. Elapsed for each report
  covers its own pass.

### 3. Engine change

Terminal events (`Done`, `Skipped`, `Failed`) gain `Files []string`: the repoRoot-relative files
the linter processed. The renderer counts unique files across events; it never re-derives file
selection.

- `buildJobs` already holds the linter's matched `files` (absolute, from `Files(...)`); `Skipped`
  and `Failed` events it sends directly carry them relativized to `repoRoot`.
- For `Done` and a `Failed` from `runJob`, `linterState` accumulates the union of the jobs'
  `batch` files (`resolvedDir`-relative) remapped to repoRoot-relative with the existing
  `remapPaths`, deduplicated with `dedupeStrings`, the same way `changedFiles` is folded today.
- `Files` is set for the linter's whole file set on a `Failed` from `runJob` (not only the failing
  batch), so a failed linter's files still count as checked. `Running` events are unchanged.
- Elapsed time is not an engine concern: the CLI measures it (`time.Now()` before the first
  `engine.Run`, `time.Since` at `Close`).
- The run log is unaffected (`logLinterEnd` ignores `Files`).

### 4. `runlog.Writer.Name()`

`func (w *Writer) Name() string` returns the run file's stem: the file name without `.jsonl`, i.e.
what `rtunk logs list` prints and `rtunk logs show` accepts. `open` (`pkg/trunk/runlog/writer.go`)
stores it on the `Writer`. A nil `*Writer` (logging disabled, a valid no-op writer) returns `""`,
consistent with the package's nil-is-a-no-op rule. The CLI passes it as `Summary.RunLog`.

`Name()` is called after the run, so it also works for the `check --fix` case where one log spans
both passes: both reports reference the same uid.

### 5. CLI flag and wiring

- `check` and `fmt` gain `--no-progress` (bool). It is not added to `PrintFailures`-style
  compatibility no-ops: it has an effect. The flag is also documented in docs/cli.md and
  docs/ux.md (implementation plan task, not this spec).
- `check.go`/`fmt.go`/`fmt_stability.go` replace `printEvent`, `printFmtEvent`, `printReport`,
  `printFmtReport`, `printFmtCheckReport` and `formatFinding` with the renderer. The
  aggregate-only helpers (`drainRunEvents`, `collectChangedByLinter`) keep their return values for
  exit codes and unstable-format attribution but take `render.Renderer.Event` instead of a print
  callback.
- Exit codes are unchanged: `1` on findings (`rtunk: check found N issue(s)`), a failed linter,
  `fmt --check` with files to reformat, `unstableFormatError`; `0` otherwise. Errors printed by
  `cmd/rtunk/main.go` are unchanged.

### 6. Migration and breaking change

- The old `file:line severity [rule] message` lines and the
  `N issue(s) in M file(s)` / `N file(s) reformatted` summaries disappear from stdout; the
  `running|done|skipped|failed` stderr lines are replaced. Anything scraping them breaks. Stable
  machine output is `--format json|sarif` in sub-project #2.
- Tests asserting the old output (e.g. `a.go:1 error no rule`, the `printReport` /
  `printFmtReport` / `printFmtCheckReport` unit tests, CLI tests checking the summary line) are
  replaced by golden expectations on the new format.
- `PrintFailures` stays a no-op flag (failures are always reported); its help text is updated to
  point at the `FAILURES` section instead of `printEvent`.

## Non-goals

- bubbletea or any progress/TTY library; colors; the TTY live view (sub-project #3).
- `--format human|sarif|json` (sub-project #2); the renderer seam exists, the flag does not.
- Clickable OSC 8 links, sorting by severity (both deferred in docs/ux.md).
- `linters list` / `actions list` (sub-project #4).
- Changing `output.Finding`, the run-log schema, file selection or exit codes.

## Testing

- **Renderer golden tests** (`internal/cli/render`, table-driven, synthetic `[]engine.Event` plus
  a `Summary`, stdout and stderr asserted separately):
  - findings across several files (alphabetical files, line/column ordering, repeated issues not
    folded, severity mapping error/warning/info to high/medium/low, empty `RuleID`);
  - a `Failed` linter with and without `RunLog` uid (`FAILURES` line with and without the
    `rtunk logs show` tail);
  - a `Skipped` linter (stderr line, `Skipped` report line);
  - no findings / clean run (clean footer); zero files;
  - `fmt`: changed files, `--check` wording, nothing changed, `--verify-stable` merged list;
  - `NoProgress` drops every stderr line, `Running` events never printed, `NO_COLOR` produces
    the same bytes (no escapes in either case).
- **CLI-level test** (`internal/cli`): `check` and `fmt` with `--no-progress` print no progress on
  stderr and the same stdout report; without it stderr has one line per finished linter; exit
  codes unchanged for findings, failure and clean runs; `check --fix` produces the formatter
  report then the check report.
- **Engine test** (`pkg/trunk/engine`): `Done`, `Skipped` and `Failed` events carry `Files`
  (repoRoot-relative, deduplicated, includes files from a `RunFrom`-resolved batch); `Running`
  events have none.
- **Runlog test** (`pkg/trunk/runlog`): `Name()` equals the file stem that `List` reports and
  `Load` accepts; a nil `*Writer` returns `""`.

## Open questions

None unresolved. Exact column alignment, glyph choice on the stderr progress lines and the
singular/plural wording are tuned in the golden tests, not fixed by this spec.
