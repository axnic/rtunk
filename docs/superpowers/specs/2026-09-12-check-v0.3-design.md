# `rtunk check` (v0.3) — Design Spec

## Goal

Implement ROADMAP.md's v0.3 milestone: run enabled linters against source files and report
findings, strictly read-only (no file mutation — that's v0.4's `check --fix`/`fmt`).

- `rtunk check [paths...]` — run enabled checks against given paths, or the whole repo if none.
- `rtunk check enable <id>[@version]` — enable one or more linters.
- `rtunk check disable <id>` — disable one or more linters.
- `rtunk check list` — list all linters available for the current configuration.

## Non-goals (explicit, ruled during brainstorming)

- **Output format coverage**: only `sarif` and `pass_fail` are parsed. Real trunk-io plugin data
  (`~/Library/Caches/rtunk/plugins/*.json`, 129 linters / 124 with commands) shows 79/124 linters
  (64%) use only these two formats plus `rewrite` (which isn't run by `check` at all — see below).
  The remaining 45 linters use one of ~25 bespoke formats (`shellcheck`, `markdownlint`, `regex`,
  `eslint`, `mypy`, ...) that are undocumented, hardcoded parsers inside trunk's closed-source
  binary — each would need reverse-engineering from the tool's real output. Deferred to a
  follow-up plan, mirroring the node-first-then-5-more pattern already used for runtimes. A linter
  whose command uses an unsupported `Output` value is skipped with a clear, non-fatal note.
- **Formatter commands are never run.** Any `Command` with `Formatter: true` (`Output: "rewrite"`)
  belongs to v0.4's `fmt`, not v0.3's `check`. `check` only runs commands with `Formatter: false`.
- **`RunFrom` and `SandboxType` are not implemented.** Of ~200 real commands surveyed, `RunFrom`
  is empty for 172 (run from repo root, the only case this plan handles) and `SandboxType` is
  empty for 186 (run directly against real files, ditto). The ~35 commands needing a non-default
  `RunFrom` or `SandboxType` are skipped with a clear note — same treatment as an unsupported
  output format. None of the sarif/pass_fail linters checked during brainstorming needed either.
- **No git-diff "changed files only" default.** ROADMAP.md's v0.3 wording is literal: given paths,
  or the whole repo if none. A `--all`-vs-default change-detection flag is a v1.0 CLI-compatibility
  concern, not stated for v0.3.
- **No `--output json`/sarif report flag.** Plain-text report only; add later if needed (YAGNI).
- **`.rtunk/user.yaml` local override does not exist yet** (grepped `pkg/trunk/config`: zero
  hits) and is not a v0.3 ROADMAP item. `check enable`/`disable` write directly to the same
  trunk.yaml `config print` already reads — matching real trunk's own behavior of editing the
  team-shared, committed config file.
- **Only `${target}` and `${tmpfile}` are templated** in a `Command.Run` string. These cover
  113 and 13 of ~200 real commands surveyed respectively (many overlapping). The remaining
  template vars (`${plugin}`, `${workspace}`, `${linter}`, `${cachedir}`, `${cwd}`,
  `${compile_commands_dir}`, `${compile_command}`, `${REPO_DIR}`, `${shared_cachedir}`,
  `${tmpdir}`) are used by 1-4 linters each — a command using one of these is skipped with a
  clear note (same unsupported-feature treatment as output format/RunFrom/SandboxType).

## Architecture

New package `pkg/trunk/check`, mirroring `pkg/trunk/download`'s separation (engine package, thin
CLI wiring in `internal/cli`).

### `pkg/trunk/check/match.go` — file-to-linter matching

```go
// Files resolves which of paths match linter's Files (ids into cfg.Lint.Files), walking
// directories recursively. A file matches a FileType if any of its own
// Extensions/Filenames/Regexes/Shebangs/RequiredYAMLKeys match, or if any FileType it Inherits
// from matches (Inherit is resolved recursively, cycle-safe).
func Files(cfg config.Config, linter config.Linter, paths []string) ([]string, error)

// matchesFileType reports whether path (whose contents are read lazily, only if a Shebangs or
// RequiredYAMLKeys check needs them) matches ft, resolving ft.Inherit against registry.
func matchesFileType(registry map[string]config.FileType, ft config.FileType, path string, seen map[string]bool) (bool, error)
```

- `Extensions`: case-insensitive suffix match on the basename (`.go`, `.yaml`, ...).
- `Filenames`: exact basename match (`Dockerfile`, `go.mod`, ...).
- `Regexes`: matched against the full path (as given/discovered, forward-slash-joined).
- `Shebangs`: only checked for extensionless files; read the first line, strip `#!`, match
  against `env <shebang>` or a direct interpreter path ending in `/<shebang>` or `<shebang>`.
- `RequiredYAMLKeys`: only checked when the file parses as YAML; the file matches only if the
  top-level mapping contains all of the given keys. A parse failure here means "does not match"
  (returns false, not error) — an unrelated YAML file failing to parse as this file type's shape
  isn't a `check` error, it's a non-match.
- No paths given → walk from the repo root (`.` relative to the resolved trunk.yaml's directory,
  matching how `findTrunkYAML` already locates the config).
- Paths given → each expanded (directories walked recursively, files taken as-is).
- `.git/` and the cache dir are always skipped during a repo-root walk.

### `pkg/trunk/check/run.go` — command execution

```go
// Finding is one normalized check result.
type Finding struct {
	Linter   string
	File     string
	Line     int    // 0 when the format doesn't report one (pass_fail)
	Column   int    // 0 when not reported
	Severity string // "error" (default) — sarif maps its own levels; pass_fail has only one level
	RuleID   string
	Message  string
	URL      string // IssueURLFormat with RuleID substituted, when both are set
}

// Phase mirrors download.Phase's shape for a familiar event stream.
type Phase int

const (
	Running Phase = iota
	Done
	Skipped // unsupported output format / RunFrom / SandboxType / template var
	Failed  // the linter's own command errored (not a lint finding — a real execution failure)
)

type Event struct {
	Phase    Phase
	Linter   string
	Findings []Finding // set on Done
	Note     string    // set on Skipped (why) or Failed (error text)
	Err      error      // set on Failed
}

// Run executes every enabled linter's non-formatter commands against the files matched under
// paths, downloading any missing tool/runtime shim first (via download.Download, same as execCmd),
// and streams one Event per linter.
func Run(cfg config.Config, cacheDir string, paths []string) (<-chan Event, error)
```

- For each `cfg.Lint.Definitions` linter (already trimmed to enabled+used by `config.Resolve`):
  - Resolve matched files via `match.Files`. Zero matches → no event at all (nothing to report).
  - For each `Command` with `Formatter == false`:
    - `RunFrom != ""` or `SandboxType != ""` → `Skipped`, note naming the field and value.
    - `Run` contains any `${...}` placeholder other than `${target}`/`${tmpfile}` → `Skipped`,
      note naming the placeholder.
    - `Output` not in `{"sarif", "pass_fail"}` → `Skipped`, note naming the format.
    - Otherwise: a `Command.Run` string is a shell command line referencing its tool(s) by bare
      name (e.g. `"shellcheck ${target} -f json --external-sources"`), not a path — it must run
      through a shell with those names resolvable on `PATH`. For every id in `linter.Tools`,
      resolve its version via `download.ResolveVersion(cfg.Lint.Enabled, id,
cfg.Tools[id].KnownGoodVersion)` (exported, already used the same way by
      `internal/cli/config.go`'s `resolvedVersionFor` — `pkg/trunk/check` calls it directly rather
      than depending on `internal/cli`) and resolve/download its shim exactly like `execCmd` does
      (`download.Download` if `download.ShimPath(...)` isn't already on disk), then collect
      `filepath.Dir` of each
      resulting shim path into a `PATH` prefix. Substitute `${target}` (space-joined, shell-quoted
      matched files when `Batch`, else one invocation per file) and `${tmpfile}` (a fresh
      `os.CreateTemp` path per invocation, removed after) into `Run`, then execute via
      `exec.Command("sh", "-c", substituted)` with `Env: append(os.Environ(), "PATH="+shimDirs+
string(os.PathListSeparator)+os.Getenv("PATH"))` and `Dir` set to the repo root, capturing
      stdout+stderr+exit code.
    - Exit code in `ErrorCodes` → `Failed` (a real tool crash — e.g. shellcheck's `ErrorCodes:
[2]`). Every other exit code parses normally: real plugin data confirms `SuccessCodes`
      already enumerates every "ran fine, here's the verdict" code including "found issues" ones
      (`ansible-lint sarif` → `[0, 2, 5]`, `codespell sarif` → `[0, 65]`, pre-commit-hooks
      `pass_fail` → `[0, 1]`) — there is no third bucket to invent. For `sarif`: parse the JSON
      regardless of which non-error code was returned (0 findings and many both parse the same
      way). For `pass_fail`: exit `0` → no finding; any non-zero, non-`ErrorCodes` exit → one
      `Finding` per targeted file.
  - Emit one `Done` event per linter with all its accumulated `Finding`s (across all its
    commands and invocations), or one `Skipped`/`Failed` event when nothing could run.

### `pkg/trunk/check/parse.go` — output parsing

```go
// ParseSARIF decodes the subset of the SARIF JSON schema trunk-io plugins actually emit
// (runs[].results[] — ruleId, level, message.text, locations[].physicalLocation) into Findings.
// A result with no physicalLocation is skipped (rare, tool-level messages) rather than erroring.
func ParseSARIF(data []byte, linter string) ([]Finding, error)

// ParsePassFail builds one Finding per file when the command's exit code was non-zero (and not
// in ErrorCodes) — pass_fail carries no line/column/rule, only "this file didn't pass".
func ParsePassFail(linter string, files []string) []Finding
```

SARIF `level` → `Severity`: `"error"` → `"error"`, `"warning"` → `"warning"`, `"note"`/unset →
`"info"`. Location's `physicalLocation.artifactLocation.uri` → `File` (repo-root-relative, as
SARIF from these tools already emits it); `region.startLine`/`startColumn` → `Line`/`Column`
(0 when absent).

### `internal/cli/check.go` — CLI surface

```go
type checkCmd struct {
	Run     checkRunCmd     `cmd:"" default:"1" help:"Run enabled checks."`
	Enable  checkEnableCmd  `cmd:"" help:"Enable one or more linters."`
	Disable checkDisableCmd `cmd:"" help:"Disable one or more linters."`
	List    checkListCmd    `cmd:"" help:"List all linters available for the current configuration."`
}

type checkRunCmd struct {
	Paths []string `arg:"" optional:"" help:"Paths to check (default: whole repository)."`
}

type checkEnableCmd struct {
	ID []string `arg:"" help:"Linter id(s) to enable, optionally @version."`
}

type checkDisableCmd struct {
	ID []string `arg:"" help:"Linter id(s) to disable."`
}

type checkListCmd struct{}
```

- `checkRunCmd.Run`: resolves config, calls `check.Run`, drains the event channel, prints a
  plain-text report and returns the error described under "Report format" below.
- `checkEnableCmd`/`checkDisableCmd`: load the config file's raw bytes, decode into a
  `*yaml.Node` document, walk to the `lint` mapping's `enabled` sequence node (creating an empty
  `lint:`/`enabled:` node if entirely absent — a valid trunk.yaml need not pre-declare an empty
  list), splice each id in (skip if already present) or out (skip if absent), re-encode with
  `yaml.Marshal` on the node, write back to the same file path `findTrunkYAML` resolved.
  `enable` accepts an optional `@version` pin appended to the written entry, matching trunk.yaml's
  own `enabled: [id@version, ...]` syntax the config package already parses elsewhere
  (`enabledIDs` in `pkg/trunk/config/filter.go` strips it the same way).
- `checkListCmd.Run`: prints each `cfg.Lint.Definitions` entry's name + description, marking
  enabled ones — same data `config print` already exposes, just a narrower/friendlier listing.

### Report format (plain text, printed by `checkRunCmd.Run`)

```
path/to/file.go:12:4 error [rule-id] Some message here (https://example.com/rules/rule-id)
path/to/other.py error [check-added-large-files] file did not pass
...

3 issues in 2 files (2 linters skipped: cspell [unsupported output format "regex"], circleci [unsupported RunFrom])
```

Findings sorted by file, then line (0 sorts first), then column. Trailing summary line always
printed; the skipped-linters parenthetical only appears when at least one linter was skipped.
`cmd/rtunk/main.go` only supports exit 0 (nil error) / exit 1 (any error) today — no
per-condition exit code plumbing exists, and adding one is out of scope for this plan. So:
`checkRunCmd.Run` returns nil (exit 0) only when there were zero findings and zero `Failed`
events; a `Failed` event's error is returned as-is (its message reaches stderr via `main.go`'s
existing `"rtunk:", err` print); any findings with no `Failed` event return a plain
`fmt.Errorf("rtunk: check found %d issue(s)", n)` after the report has already been printed to
stdout — both cases exit 1, distinguished only by the report text already on screen, matching
trunk's own `trunk check` (its exit code doesn't distinguish "found issues" from "tool crashed"
either).

## Testing approach

- `match_test.go`: exact-path assertions for each `FileType` matcher kind (extension, filename,
  regex, shebang, required-yaml-keys) plus one `Inherit` composition case and one cycle-safety
  case (`Inherit` cycle must not hang).
- `run_test.go`: a fake linter definition + a real (compiled, not shell-scripted — the same
  ENOEXEC lesson from the python runtime work applies here) fake tool binary that emits real
  SARIF and real pass_fail-style exit codes, asserting the exact `Finding` values produced —
  never just "no error". Separate cases for `Batch: true` vs `false`, `SuccessCodes`/`ErrorCodes`
  boundaries, and each `Skipped` reason (bad `Output`, non-empty `RunFrom`, non-empty
  `SandboxType`, an unsupported template var).
- `parse_test.go`: `ParseSARIF` against a real SARIF sample captured from an actual plugin's
  documented shape (not hand-waved), asserting exact `Finding` field values including a
  no-physicalLocation result being skipped, not erroring.
- `internal/cli/check_test.go`: `checkEnableCmd`/`checkDisableCmd` asserting the exact resulting
  YAML bytes (id added/removed, comments elsewhere in the file preserved, `@version` pin
  round-trips), plus idempotency (`enable` on an already-enabled id is a no-op, `disable` on an
  absent id is a no-op) and the from-scratch case (a trunk.yaml with no `lint:` key at all).
  `checkRunCmd`/`checkListCmd` asserting the exact printed report text for a small fixture config.

## Global constraints (carried into every task)

- No new `go.mod` dependencies — SARIF parsing is plain JSON (`encoding/json`), YAML node editing
  uses the already-vendored `gopkg.in/yaml.v3`.
- Every test asserting a file path/`Finding` must assert the exact value, never just "no error" —
  the standing lesson from this session's v0.2 node-shim and python-package regressions, both of
  which shipped because no test checked the exact resulting path/behavior.
- Commits signed (`-S`), commitlint conventions per `.agents/skills/git-commit/SKILL.md`.
- `go build ./... && go vet ./... && go test ./... -count=1` clean before every task is considered
  done.
