# v0.11 Catalog Fidelity — Execution Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close 4 of ROADMAP.md v0.11's "catalog fidelity" items — the ones about *how a command executes* rather than what gets installed or suggested: per-command run timeouts, per-command one-time setup, per-command concurrency caps, and overlapping-linter finding suppression. This is the third of five independent plans covering v0.11; the first two (cache consolidation, shared provisioning) already merged to `main`.

**Architecture:** `pkg/trunk/config.Linter` already has a `RunTimeout string` field (parsed, never consulted — `docs/architecture/inconsistencies.md` entry, catalog occurrence count 8). `pkg/trunk/config.Command` has no `PrepareRun`/`MaxConcurrency`/`DisableUpstream` fields at all yet — the real catalog declares `prepare_run`, `max_concurrency`, `disable_upstream` on commands, and rtunk's YAML unmarshal silently drops anything with no matching struct field, so these three are invisible today, not just unconsulted. All four hook into the same two places: `pkg/trunk/engine/engine.go`'s `job`/`runBatch`/`Run` (which already threads one piece of per-run shared state, `inPlaceMu *sync.Mutex`, through every worker exactly the way this plan's new shared state needs to), and — for the cross-linter suppression only — `internal/cli/check.go`'s `drainEvents`, which already collects every linter's findings into one slice before rendering.

**Tech Stack:** Go stdlib only (`context`, `sync`, `time`).

**Spec:** [ROADMAP.md](../../../ROADMAP.md), "v0.11 — Cache, provisioning, and catalog fidelity", the four bullets: "Per-command run timeouts", "Per-command setup runs before first use", "Per-command concurrency caps are honored", "Overlapping linters don't double-report." Background and real-catalog occurrence counts: [docs/architecture/inconsistencies.md](../../architecture/inconsistencies.md), "Declared-but-inert catalog fields" section, and [docs/architecture/plugin-model.md](../../architecture/plugin-model.md)'s field-occurrence table.

## Global Constraints

- No Windows support — no Windows-specific branches.
- No real vendored plugin catalog exists in this repo to check `prepare_run`'s and `disable_upstream`'s exact real-world YAML shapes against — `docs/architecture/inconsistencies.md` itself rates both "inferred impact — not observed against [a real linter declaring this / a real overlapping pair]." This plan's Task 2 and Task 4 make an explicit, documented, defensible design choice for each rather than guessing at a shape nothing in this codebase can confirm; if either task's implementer finds evidence of the real shape (a fixture, a comment, anything this plan's own research missed), that evidence wins over this plan's assumption — say so in the report either way.
- `job` (engine.go) already carries `linter config.Linter` and `cmd config.Command` per job — every new field this plan adds to `Command`/`Linter` is automatically reachable from any job without further plumbing.
- `Run`'s existing `inPlaceMu *sync.Mutex` is threaded through `runJob`→`runBatch` as a pointer built once, before the worker pool starts, and read (never rebuilt) by every worker — this plan's new shared state (semaphores, once-flags) must follow that exact same lifecycle: built once in `Run`, before `wg.Go` starts any worker, passed down as an argument, never mutated concurrently in a way the existing pattern doesn't already handle.
- A canceled or timed-out invocation must keep reporting as a `Failed` event through the *existing* error-return path (`runOneInvocation`'s `c.Run()` returning a non-`*exec.ExitError` error propagates up through `runBatch`'s existing `if err != nil { return nil, nil, err }` into `runJob`'s existing `Failed` event) — do not add a second, parallel failure-reporting mechanism for the timeout case.

## Review Focus

- A linter with no `run_timeout` declared (the overwhelming majority of the real catalog — only 8 occurrences) must behave identically to before this plan: no `context.WithTimeout` wrapping at all, not even a zero-duration no-op one.
- A command with no `max_concurrency` declared must never be gated by a semaphore of size 0 (which would deadlock every invocation of it) — the semaphore must only exist for commands that actually declare a positive value.
- Two different commands of the *same* linter, each with their own `max_concurrency`, must be capped independently — a shared semaphore keyed only by linter name (not linter+command) would wrongly conflate them.
- `prepare_run` must run at most once per `engine.Run` call even when many files batch into many separate jobs for the same command (a `sync.Once`, not a plain boolean check-then-set, which would race under this package's own worker-pool concurrency).
- `disable_upstream` suppression must never apply when the "upstream" linter it names is enabled but produced zero findings, or is not enabled at all — suppression is real only when both are enabled AND the superseded one actually has findings to suppress.

Implement (a) — it's a few more lines and is the only version that's actually correct under concurrency.

```go
	if sem, ok := cmdSems[j.linterName+"/"+j.cmd.Name]; ok {
```

## Task 4: Overlapping linters don't double-report

**Files:**
- Modify: `pkg/trunk/config/definitions.go` (`Command` — add `DisableUpstream []string`)
- Modify: `internal/cli/check.go` (`drainEvents`)
- Test: `internal/cli/check_test.go` (or wherever `drainEvents`'s own existing tests live — find it first)

**Interfaces:**
- Consumes: `output.Finding.Linter string` (existing — every `Finding` already carries which linter produced it, per `internal/cli/render/base.go`'s own use of `f.Linter` seen in this plan's research).
- Produces: `config.Command.DisableUpstream []string` (new, `yaml:"disable_upstream,omitempty"`) — a list of linter ids this command's own linter supersedes. `drainEvents` (or a small new helper it calls) drops every `Finding` whose `Linter` matches one of the *enabled* superseded ids, but only when the superseding linter itself is also enabled and produced at least one finding of its own — see this task's Review Focus item on exactly this condition.

**Design note (read before starting — this is the plan's documented, best-effort interpretation):** the real shape of `disable_upstream` (a single upstream id? a list? does it live on the `Command` or the `Linter`?) has no confirmed example in this codebase — `docs/architecture/inconsistencies.md` rates this "inferred impact — not observed against a real overlapping pair." This plan models it as a `[]string` on `Command` (a command can supersede more than one upstream linter — e.g. a combined linter replacing several narrower ones is a plausible real shape) and applies **whole-linter suppression** (drop every finding from a superseded, enabled linter entirely) rather than attempting fine-grained per-finding "same issue" matching (matching by file+line+rule across two different tools' own differing rule-naming schemes has no existing precedent anywhere in this codebase to build on, and inventing one risks false negatives that hide real, distinct findings). If a future real catalog example shows a different shape, that's a follow-up, not a defect in this documented choice.

```go
func suppressUpstream(cfg config.Config, findings []output.Finding) []output.Finding {
	produced := map[string]bool{}
	for _, f := range findings {
		produced[f.Linter] = true
	}

	suppress := map[string]bool{}
	for id, l := range cfg.Lint.Definitions {
		if !produced[id] {
			continue // this superseding linter found nothing; don't suppress on its behalf
		}
		for _, cmd := range l.Commands {
			for _, upstream := range cmd.DisableUpstream {
				if produced[upstream] {
					suppress[upstream] = true
				}
			}
		}
	}
	if len(suppress) == 0 {
		return findings
	}

	out := findings[:0]
	for _, f := range findings {
		if !suppress[f.Linter] {
			out = append(out, f)
		}
	}
	return out
}
```
